# Welder 中文精读

## 1. 从“算子图”转向“tile 流量图”

Welder 的出发点是：在新 GPU 上，Tensor Core 算力增长速度超过内存带宽，很多模型即使包含 GEMM/Conv，端到端仍被数据移动限制。传统方案有两个断层：

- library/auto-scheduler 把每个 operator 单独做到很快；
- graph compiler 用固定规则融合 operator。

前者看不到跨算子复用，后者不知道融合后的 tile shape 是否适合硬件。Welder 用 tile-graph 把两者放进同一个优化空间。

图 2 的反例很重要：分别最优的算子 tile 组合起来未必端到端最优；为了在 operator 边界复用，需要联合调整两侧 tile。

## 2. Operator-tile

一个 operator-tile 表示“为生成某块输出，需要加载哪些输入 tile、执行哪些计算、写出哪些结果”。例如卷积输出 tile 会反推输入 halo；elementwise 通常一一对应。

把完整 tensor 替换为 tile 后，中间结果不必总在 HBM materialize。若 producer 与 consumer 的 tile 对齐，可以在更高层 memory 中直接传递。

## 3. Tile-graph 与多级存储

tile-graph 的 edge 不只表示依赖，还记录 producer 的 tile 在哪级 memory 被 consumer 复用：

$$
\operatorname{Cost}(P)=\sum_{\ell\in\text{memory levels}}
\operatorname{Traffic}_{\ell}(P)\cdot \operatorname{UnitCost}_{\ell}.
$$

计划 $P$ 同时选择：

- operator 的 tile shape；
- 相邻 operator 是否连接；
- 连接发生在 register/shared/device 哪一层；
- 超出 device memory 时是否延伸到 host memory。

## 4. 为什么搜索可以分层

全局联合搜索会组合爆炸。论文观察到：优化某一级 memory traffic 时，较低层的具体 tile 实现可暂时抽象；因此从较高层到较低层分解搜索。

流程大致是：

1. GraphConnecting 决定边在何种 memory level 连接；
2. ExtractSubgraph 提取同层可联合调度的子图；
3. SubGraphTiling 搜索满足容量与并行度约束的 tile；
4. profile/cost model 在候选中选延迟较低者；
5. 递归进入下一存储层。

这不是数学上对任意硬件都严格独立，而是一个可利用的结构性近似。设备接口需要提供容量、transaction、并行度等信息。

## 5. Codegen

Welder 将 tile plan 降为：

- CUDA 的 thread block、warp、SIMT/TensorCore schedule；
- Graphcore IPU 的 tile 映射；
- 必要时把大模型的 tensor 分块跨 host/device 流动。

它仍依赖底层 kernel generator。论文明确承认，在 compute-intensive 部分，如果 backend 生成的 GEMM 不如厂商库，整体收益会受限。因此 Welder 与更强的单 kernel codegen 是互补关系。

## 6. 端到端结果怎么读

论文覆盖 BERT、Swin-T、MobileNet、NAFNet、Restormer、NeRF 等 10 个模型、34 个配置。batch 1 的一组结果中，Welder 相对 TensorRT 平均约 1.47×；在 TensorRT 已有成熟手写规则的 BERT/Swin-T 上差距小，而在 NAFNet 等新图结构上最高约 3.09×。

TensorCore 加快 compute 后，剩余 memory traffic 占比上升，因此 fusion 价值可能更大。batch 1 TensorCore 组相对 TensorRT 平均约 1.53×；但不同图使用的模型集合和可运行基线不同，不应把所有最高值并列当成同一实验。

Welder 自动发现约 300 个 fused subgraphs，其中 89 个包含至少两个 reduction-based operator，说明 tile abstraction 确实扩大了规则式 fusion 的覆盖面。编译时间则是代价：搜索适用于模型重复运行，而不是一次性 workload。

## 7. 与 FusionStitching 的差异

FusionStitching 重点是让异构并行 operator 能在一个 kernel 内拼接，并估算 kernel-level latency；Welder 更强调：

- tile 是优化单位；
- 跨 operator reuse 与 intra-operator tiling 联合决定；
- 同一套抽象覆盖多级 memory；
- 目标是全图 traffic，而非局部 fusion legality。

二者不是替代关系：FusionStitching 的 composition/codegen 可以成为 Welder 类全局 planner 的下层能力。

## 8. 常见误读

### “Welder 总比 TensorRT 快 3×”

错误。3× 是特定新模型/配置的上界；成熟 Transformer 上常接近持平。必须同时标注模型、batch、精度、GPU 与 TensorCore。

### “tile 越大，复用越多，所以越快”

tile 变大会增加 shared memory/register footprint，降低 occupancy，还可能加入无用计算。

### “减少 HBM traffic 就等于减少 latency”

仅在 memory-bound 区域近似成立。若 compute、同步或 host 调度占主导，traffic 降低不会线性转成端到端加速。

## 9. 复现检查点

- 记录每层 memory 的读写 bytes，而非只记录 kernel 数。
- 固定 TensorRT/TVM/driver 版本与 autotuning budget。
- 区分 SIMT、TensorCore、FP32、FP16、batch 1/64。
- 把 compile/search 时间单独列出。
- 对动态 shape 检查是否发生重新编译或 plan cache miss。
- 验证不同 fusion plan 的数值误差，特别是 reduction reassociation。

## 10. 对今天系统的启示

TorchInductor、Triton、CuTe DSL 和 MegaKernel 系统都在不同层次重复面对 Welder 的问题：tile shape、memory placement 与跨 operator 边界不能独立决策。Welder 的具体实现会过时，但“用 tile traffic 统一 fusion 与 schedule”的观点仍很现代。

## 11. 最终判断

如果只读一篇来理解 kernel fusion 为什么会变成编译器问题，Welder 很合适。它把问题从“哪些节点合并”提升为“哪些 tile 在哪一级 memory 生产、保留和消费”，也清楚展示了收益、搜索成本和 backend 质量三者的耦合。
