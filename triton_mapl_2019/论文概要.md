# 论文概要：《Triton: An Intermediate Language and Compiler for Tiled Neural Network Computations》

## 一、基本信息

- 作者：Philippe Tillet、H. T. Kung、David Cox
- 会议：MAPL 2019
- DOI：`10.1145/3315508.3329973`
- 定位：Triton 的奠基论文
- 本地材料：[论文 PDF](paper.pdf) · [提取文本](paper.txt) · [中文解读](论文中文解读.md)

## 二、一句话结论

Triton 把 GPU kernel 的基本编程单位从“单个线程处理标量”提升为“program instance 处理一个多维 tile”，再由编译器自动完成线程映射、访存合并、共享内存管理和同步，从而用比 CUDA 更高层的代码获得接近手写库的性能。

## 三、论文要解决的问题

深度学习算子既需要高性能，又经常出现新结构、融合形式和稀疏模式。直接调用 cuBLAS/cuDNN 很快，但只能覆盖库预先实现的算子；手写 CUDA 灵活，却要求开发者掌握线程组织、共享内存、同步、bank conflict 和 coalescing。

此前 DSL 往往落在两个极端：要么抽象足够高但生成代码慢，要么性能接近 CUDA却仍暴露大量硬件细节。论文希望找到一个中间层：让程序员显式描述 tile 级算法，让编译器负责 tile 内部的细粒度并行化。

## 四、核心设计

### 4.1 Tile-level 编程模型

一个 Triton kernel 启动许多 program instance。每个 instance 看起来是顺序程序，但操作对象不是标量，而是具有静态形状的多维 tile。程序员决定 tile 之间怎样分工；编译器决定一个 tile 内的数据怎样放进线程、寄存器与共享内存。

这与 CUDA 的差别不是简单的语法糖：CUDA 代码显式写 thread-level 地址和同步，Triton 代码把一组相关元素作为整体来运算，使编译器能重新选择底层映射。

### 4.2 Triton-C、Triton-IR 与 JIT

2019 原型包含：

- C 风格前端 Triton-C；
- 基于 LLVM 的 tile-level Triton-IR；
- 在运行时根据输入形状生成、编译并选择配置的 Triton-JIT；
- 一个在 tile、micro-tile、nano-tile 参数空间中搜索的 autotuner。

今天常见的 Python DSL 和 MLIR 后端是后续演化，不能把当前 API 反投射到这篇论文。

### 4.3 PSSA 与掩码语义

tile 中不同元素可能走不同控制流。论文使用 predicated SSA（PSSA）和 `psi` 一类的合并语义，把逐元素谓词带入 IR。它使边界元素和分支能继续保持 tile 形式，而不必把整个程序降回逐线程控制流。

### 4.4 编译器自动完成的工作

机器无关阶段包括软件预取和 tile peephole 优化；机器相关阶段包括：

- hierarchical tiling：把 tile 逐级分给 warp、线程和每线程的小向量；
- 根据连续维度排列线程，生成合并的全局内存访问；
- 结合活跃区间分配共享内存并复用空间；
- 从数据依赖推导必要的 barrier；
- 搜索 tile 层级参数。

## 五、实验结果应怎样读

论文在 NVIDIA GTX 1070 上测试矩阵乘和卷积，并与 cuBLAS 10、cuDNN 7、AutoTVM、Tensor Comprehensions、PlaidML 比较。

- 多组矩阵乘上，Triton 与 cuBLAS 大体相当，部分任务达到峰值算力的 90% 以上；其他当时的 DSL 常慢 2–3 倍。
- 浅而宽的 Transformer 形状上，cuBLAS 的 split-K 等策略仍更好，说明 Triton 的搜索空间并不完备。
- 卷积使用 implicit GEMM；某些 ResNet 形状能胜过 cuDNN 的 implicit-GEMM 路径，但 cuDNN 若选择 Winograd，整体仍可能更快。
- 融合 shifted convolution 展示了 DSL 的长处：中间变换可以融合进 kernel，额外代价接近被隐藏。

论文证明的是“这种抽象能产生有竞争力的代码”，不是“所有工作负载都胜过厂商库”。

## 六、最重要的洞见

1. **抽象层级决定编译器能做什么。** 标量线程代码把布局决策写死；tile 运算保留了可供编译器优化的结构。
2. **性能可移植性依赖编译器，不等于零调优。** 用户少写硬件细节，但 tile 大小等参数仍要搜索。
3. **融合是 Triton 的天然优势。** 固定函数库擅长成熟单算子，Triton 更适合形状特殊或需要融合的新 kernel。
4. **Triton 不是“自动把任意 Python 变快”。** 这篇论文只讨论受限 DSL 和结构化张量计算。

## 七、局限

- 只有一张较旧的消费级 NVIDIA GPU，跨代、跨厂商结论不足。
- 主要实验是 GEMM 与 convolution，不能覆盖 reduction、attention、scan 等后来常见模式。
- 搜索空间只覆盖 hierarchical tiling 的有限组合。
- tensor core、量化和更复杂的硬件 intrinsic 在论文中仍属于未来工作。
- 与高度成熟厂商库的比较受算法选择影响，不能只比较同名算子的单一路径。

## 八、今天为什么仍值得读

现代 Triton 的语法、IR 和硬件支持已经大幅变化，但核心取舍没有变：开发者写 tile-level 数据流，编译器负责底层映射。理解这篇论文后，`program_id`、block pointer、mask、`tl.dot`、autotune 等现代接口就不再是零散 API，而是同一设计哲学的后续实现。
