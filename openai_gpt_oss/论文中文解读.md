## 一、一句话结论

gpt-oss-120b 与 gpt-oss-20b 是 OpenAI 发布的两个**开放权重**（open-weight）推理模型（据原文，开发过程中听取了开源社区的反馈），采用 Apache 2.0 许可并附 gpt-oss usage policy，只处理文本，面向 agent 工作流设计：强指令遵循、能用网页搜索和 Python 执行等工具、推理强度可调、可定制、输出完整思维链（CoT）、支持 Structured Outputs，并兼容 OpenAI 的 Responses API。

- **架构**：自回归的混合专家（MoE）Transformer。120b 有 36 层，总参数 116.8B，每个 token 只激活 5.1B；20b 有 24 层，总参数 20.9B，激活 3.6B。MoE 权重用 MXFP4 格式（每参数 4.25 比特），使 120b 能放进单张 80GB GPU，20b 能在只有 16GB 内存的系统上运行。
- **能力**：在推理强度为 high 时，120b 在多项基准上超过 o3-mini，并接近 o4-mini；20b 虽然小 6 倍，仍有竞争力。
- **安全**：开放权重一旦发布就无法收回，也无法在服务端加防护，所以模型卡的重点是**最坏情况评估**：OpenAI 用自家的强化学习训练栈对 120b 做了生物化学与网络安全两个方向的对抗微调，并由安全顾问组（SAG）评审，结论是即使如此也未达到 Preparedness Framework 的 High 阈值，而且发布 120b 不会显著推进开放模型的生物能力前沿。
- **边界**：它是“开放权重”而不是“开放训练全栈”：架构超参数和训练算力披露得相当具体，但预训练数据构成、后训练配方、RL 环境和训练代码都没有公开。

## 三、模型规模与参数拆解（原文第 2 节，表 1）

“120b”“20b”是简称，实际参数量分别是 116.8B 与 20.9B。表 1 给出完整拆分：

表 1：模型参数量（Unembedding 参数计入激活参数，Embedding 不计入）

| 组成 | gpt-oss-120b | gpt-oss-20b |
|---|---:|---:|
| MLP（MoE 专家部分） | 114.71B | 19.12B |
| Attention（注意力） | 0.96B | 0.64B |
| Embed + Unembed（词嵌入与输出投影） | 1.16B | 1.16B |
| Active Parameters（每 token 激活参数） | 5.13B | 3.61B |
| Total Parameters（总参数） | 116.83B | 20.91B |
| Checkpoint Size（检查点大小） | 60.8GiB | 12.8GiB |

（原文表 1，第 5 页。）**读法**：MoE 的 MLP 占总参数的比例，120b 约 98%（114.71 ÷ 116.83），20b 约 91%（19.12 ÷ 20.91），与原文“90% 以上”一致，所以“总参数”主要就是专家参数；而每个 token 只激活其中一小部分，因此计算量按激活参数（5.13B 与 3.61B）计，显存占用却要按**全部权重**计（检查点 60.8GiB 与 12.8GiB）。

下面用原文的架构数字做了一组验算（笔者验算，原文没有写这些推导），可以帮助理解表中数字的含义：

| 验算项 | 过程与结果 |
|---|---|
| 词嵌入大小 | 词表 201,088 × 宽度 2880 ≈ 0.579B；Embedding 与 Unembedding 各一份，合计 ≈ 1.158B，与表中 1.16B 吻合 |
| 激活参数 | 激活参数 ≈ Attention + Unembedding + （4 ÷ 专家数）× MLP。120b：0.96 + 0.579 + 4/128 × 114.71 ≈ 5.12B（表 5.13B）；20b：0.64 + 0.579 + 4/32 × 19.12 ≈ 3.61B（表 3.61B） |
| 单个专家的大小 | 每层 MLP 参数 ÷ 专家数：120b 为 114.71B ÷ 36 ÷ 128 ≈ 24.9M，20b 为 19.12B ÷ 24 ÷ 32 ≈ 24.9M，两个模型相同。若每个 SwiGLU 专家由三个 2880 × 2880 矩阵组成，恰好是 3 × 2880 × 2880 ≈ 24.9M，所以专家隐层宽度约为 2880（这是推算，原文没有给出） |
| 每层注意力参数 | Q：2880 × 4096，K、V：各 2880 × 512，输出投影：4096 × 2880，合计 ≈ 26.5M；乘 36 层 ≈ 0.96B，乘 24 层 ≈ 0.64B，与表一致 |
| 检查点大小 | MoE 参数按 4.25 比特、其余参数按 16 比特（假设为 BF16）估算：120b ≈ 56.8 + 3.9 ≈ 60.7GiB（表 60.8GiB）；20b ≈ 9.5 + 3.4 ≈ 12.8GiB（表 12.8GiB） |

最后一行也间接验证了第四章的说法：只有 MoE 权重被量化为 4.25 比特，其余部分保持更高精度（这里假设其余部分为 BF16）。

## 四、量化：MXFP4（第 2.1 节）

为降低显存占用，团队“在后训练中对 MoE 权重做了 MXFP4 格式的量化”（原文：post-trained the models with quantization of the MoE weights to MXFP4），权重平均每参数 4.25 比特。MoE 权重占总参数的 90% 以上，把它们量化后，大模型能放进单张 80GB GPU，小模型能在只有 16GB 内存的系统上运行。检查点大小见表 1。

背景说明（来自 OCP Microscaling 格式规范，不在模型卡里）：MXFP4 以 32 个元素为一块，每块共享一个 8 比特的缩放因子，块内每个元素用 4 比特浮点表示，平均每元素 4 + 8/32 = 4.25 比特。

要点：

- 原文措辞是 “post-trained the models with quantization of the MoE weights”，字面更像是在**后训练阶段**就带着量化做训练，而不是训练结束后再单独做训练后量化（PTQ）；但具体方式（是否量化感知训练、梯度如何处理）原文没有写，不宜过度解读。
- “能放进 80GB 或 16GB”只说明权重能驻留。实际服务还需要 KV cache、激活值、运行时工作区和并发余量；MXFP4 的实际速度也取决于硬件和推理引擎是否原生支持这一格式。

## 五、架构（第 2.2、2.3 节）

两个模型共享同一套设计，只在层数和专家数上不同。

表（汇总）：gpt-oss 的架构超参数

| 项目 | gpt-oss-120b | gpt-oss-20b |
|---|---|---|
| 层数 | 36 | 24 |
| 残差流宽度 | 2880 | 2880 |
| 归一化 | 在每个注意力块和 MoE 块之前对激活做 RMSNorm（Pre-LN 位置） | 同左 |
| 每个 MoE 块的专家数 | 128 | 32 |
| 每 token 选择的专家数 | top-4 | top-4 |
| 专家激活函数 | gated SwiGLU（实现不常规，含 clamping 与残差连接） | 同左 |
| Query 头 | 64 个，每个 64 维 | 同左 |
| Key-Value 头 | 8 个（Grouped Query Attention，GQA） | 同左 |
| 注意力模式 | 带状窗口（bandwidth 128 token）与全稠密交替 | 同左 |
| 位置编码 | RoPE；稠密层用 YaRN 把上下文长度扩展到 131,072 token | 同左 |
| softmax 分母 | 每个注意力头有一个可学习偏置 | 同左 |
| 分词器 | o200k_harmony，共 201,088 个 token | 同左 |
| 总参数 / 激活参数 | 116.83B / 5.13B | 20.91B / 3.61B |

（来自原文第 2.2、2.3 节与表 1，第 5、6 页。）

### 5.1 混合专家（MoE）

每个 MoE 块由固定数量的专家（120b 为 128 个，20b 为 32 个）和一个标准的线性路由器（router projection）组成，路由器把残差激活映射成对每个专家的打分。两个模型都为每个 token 选出得分最高的 4 个专家，并且只在被选中的 4 个专家上做 softmax，用它给各专家输出加权。按这段文字写出的计算是：

$$
s=W_r x,\qquad \mathcal{T}=\operatorname{TopK}(s,4),\qquad g_i=\frac{e^{s_i}}{\sum_{j\in\mathcal{T}}e^{s_j}}\ \ (i\in\mathcal{T}),\qquad y=\sum_{i\in\mathcal{T}}g_i\,E_i(x)
$$

其中 $x$ 是一个 token 在该层的（归一化后）激活，$W_r$ 是路由器的线性投影，$s$ 是对全部专家的打分，$\mathcal{T}$ 是被选中的 4 个专家，$E_i$ 是第 $i$ 个专家（一个门控 SwiGLU 的 MLP），$y$ 是 MoE 块的输出。这是对原文文字描述的形式化，原文没有给出公式。原文没有说明是否有负载均衡损失、偏置项等训练细节。

专家的激活函数是 gated SwiGLU，脚注说明其实现“不常规”，包含 clamping（截断）和残差连接，细节没有展开。

### 5.2 注意力

- **带状窗口与稠密层交替**：沿用 GPT-3 的做法，注意力层在“带状窗口”和“全稠密”两种模式之间交替，带宽为 128 token。带状层只看附近的 128 个 token，成本不随序列长度增长；稠密层周期性地提供全局通信。
- **头的配置**：每层有 64 个 query 头，每头 64 维，使用 Grouped Query Attention，只有 8 个 key-value 头，也就是每 8 个 query 头共享一组 K、V，以减小 KV cache。
- **位置编码与长上下文**：使用旋转位置编码（RoPE），并用 YaRN 把稠密层的上下文长度扩展到 131,072 个 token（128K）。
- **可学习的 softmax 分母偏置**：每个注意力头在 softmax 的分母里有一个可学习的偏置，类似 off-by-one attention 与 attention sink，使注意力机制可以“不关注任何 token”。若记第 $i$ 个位置的注意力打分为 $z_i$，该头的偏置为 $b$，则注意力权重可写成

$$
\alpha_i=\frac{e^{z_i}}{e^{b}+\sum_{j}e^{z_j}}
$$

此时所有真实 token 的权重之和 $\sum_i\alpha_i<1$，剩余的部分相当于“把注意力放在没有 token 的地方”。（这是对原文文字描述的形式化；每个头一个标量偏置是笔者对“a learned bias”的读法。）

### 5.3 一个笔者估算：KV cache 有多大

假设注意力层严格按“带状、稠密”交替（稠密层占一半），且 KV cache 以 BF16 存储（这两点都是假设）。每个稠密层每个 token 要存 $2\times 8\times 64=1024$ 个数（K 与 V，8 个头，64 维）。

- gpt-oss-120b：18 个稠密层，每 token $18\times1024\times2\ \mathrm{B}=36{,}864\ \mathrm{B}$，在 131,072 token 的满长度下约 4.5GiB。
- gpt-oss-20b：12 个稠密层，每 token 24,576 B，满长度下约 3.0GiB。
- 带状层只需缓存最近 128 个 token，量级只有几 MB，可以忽略。

这个估算说明“交替带状窗口”确实把长上下文的 KV cache 砍掉了大约一半，但在 128K 上下文、多路并发时，KV cache 仍然是权重之外需要认真预留的显存（实际占用取决于推理引擎的实现）。

### 5.4 分词器

所有训练阶段都使用 o200k_harmony 分词器，已在 TikToken 库开源。它是字节对编码（BPE），在 GPT-4o 与 o4-mini 使用的 o200k 分词器基础上，增加了 harmony 聊天格式所需的专用 token，词表共 201,088 个。

## 六、预训练与训练资源（第 2.4 节）

- **数据**：纯文本数据集，规模为数万亿 token，重点是 STEM、代码和通用知识。为提高安全性，预训练时过滤了有害内容，特别是危险的生物安全知识，做法是复用 GPT-4o 的 CBRN（化学、生物、放射、核）预训练过滤器。模型的知识截止日期为 2024 年 6 月。
- **训练硬件与软件**：在 NVIDIA H100 GPU 上用 PyTorch 训练，使用专家优化的 Triton 内核（原文脚注指向 triton 仓库的 triton_kernels 目录）。两个模型都用了 FlashAttention 系列算法来降低显存需求、加快训练（见[FlashAttention](../flash_attention/论文中文解读.md)）。
- **训练量**：训练 gpt-oss-120b 需要 210 万 H100 小时；gpt-oss-20b 少近 10 倍（原文没有给出具体数字）。
- **没有披露的**：训练 token 的确切数目、数据配比与语种构成、学习率与批大小等超参数、MoE 负载均衡方式、数据去重和质量过滤的细节。所以不能由这份模型卡推断“它主要是英文数据”之类的结论（原文只说是纯文本，并没有说语言构成）。

## 七、后训练：推理与工具使用（第 2.5 节）

预训练之后，团队用与 OpenAI o3 类似的 CoT 强化学习技术做后训练。这一步教模型用思维链（CoT）推理和解题，也教它使用工具；由于 RL 技术相近，这些模型的“个性”与 ChatGPT 等第一方产品里的模型相似。训练数据是编码、数学、科学等领域的大量问题。具体的 RL 算法、奖励设计、数据规模、训练时长，模型卡都没有给出。

### 7.1 harmony 聊天格式（第 2.5.1 节）

训练使用一种自定义的聊天格式，称为 harmony chat format。它用专用 token 划定消息边界，用关键字参数（如 User 与 Assistant）标明消息的作者与接收者，沿用 OpenAI API 模型中同样的 System 与 Developer 消息角色。有了这些角色，模型按一个**基于角色的信息层级**来解决指令冲突：

$$
\text{System} > \text{Developer} > \text{User} > \text{Assistant} > \text{Tool}
$$

即系统消息优先于开发者消息，开发者消息优先于用户消息，工具返回的内容优先级最低。这一层级对 prompt injection 很重要：工具输出里夹带的指令不能凌驾于上层指令之上（第 9.4 节会看到模型在这方面的评测）。

格式还引入了“**通道**（channel）”，表明每条消息的预期可见范围：

| 通道 | 用途 |
|---|---|
| `analysis` | 思维链（CoT）token |
| `commentary` | 函数工具调用 |
| `final` | 展示给用户的答案 |

这使模型可以实现更高级的 agent 功能：在 CoT 中穿插工具调用，或者先给用户一段“前言（preamble）”，概述接下来较长的行动计划。原文强调：必须按开源实现与指南里说明的方式正确使用该格式，才能发挥模型的最佳能力；例如在多轮对话里，应当**删掉历史轮次中助手的推理痕迹**。

**图中文字转录与读法**（红色为特殊记号；转录为纯文本）：

```text
<|start|>system<|message|>You are ChatGPT, a large language model trained by OpenAI.
Knowledge cutoff: 2024-06
Current date: 2025-06-28

reasoning: low

# Valid channels: analysis, commentary, final. Channel must be included for every message.
Calls to these tools must go to the commentary channel: 'functions'.<|end|>
<|start|>developer<|message|># Instructions

Use a friendly tone.

# Tools

## functions

namespace functions {

// Gets the current weather in the provided location.
type get_current_weather = (_: {
// The city and state, e.g. San Francisco, CA
location: string,
format?: "celsius" | "fahrenheit", // default: celsius
}) => any;

} // namespace functions<|end|>
<|start|>user<|message|>What is the weather like in SF?<|end|>
<|start|>assistant
```

```text
<|channel|>analysis<|message|>Need to use function get_weather.<|end|>
<|start|>assistant<|channel|>commentary to=functions.get_weather <|constrain|>json<|message|>{"location":"San Francisco"}<|call|>
```

- **输入（图 17）**：system 消息写明身份、知识截止（2024-06）、当前日期、推理强度（`reasoning: low`），并规定有效通道只有 analysis、commentary、final，每条消息必须带通道，且对工具 `functions` 的调用必须走 commentary 通道；developer 消息里是指令（“用友好的语气”）和工具定义，工具以类似 TypeScript 的命名空间形式给出；最后是 user 消息，并以 `<|start|>assistant` 结尾，模型从这里开始生成。
- **输出（图 18）**：模型先在 analysis 通道里写一句 CoT（“需要用函数 get_weather”），然后在 commentary 通道里向 `functions.get_weather` 发起调用，参数约束为 JSON，参数是 `{"location":"San Francisco"}`，并以 `<|call|>` 结束，等待工具返回。
- **记号含义**：原文只给了示例，没有逐个解释记号；根据示例推断，`<|start|>` 开始一条消息并跟角色，`<|message|>` 分隔消息头与内容，`<|end|>` 结束一条消息，`<|channel|>` 指定通道，`<|constrain|>` 约束调用参数的格式，`<|call|>` 表示工具调用结束。准确语义以官方 harmony 文档和开源实现为准。
- **示例里的小出入**：developer 消息里定义的工具名是 `get_current_weather`，而图 18 里调用的却是 `get_weather`，原文如此，应是示例笔误，不影响对格式的理解；原图中 `San Francisco` 里的空格是用可见空格符显示的，上面转录为普通空格。

### 7.2 可变推理强度（第 2.5.2 节）

模型被训练成支持 **low、medium、high** 三个推理级别。级别通过系统提示里的关键字设置，例如 `Reasoning: low`（图 17 里写作 `reasoning: low`）。提高推理级别会使模型平均的 CoT 长度增加。这给了部署者一个旋钮：简单任务用 low 省延迟与成本，难题用 high 换准确率。

### 7.3 agent 式工具使用（第 2.5.3 节）

后训练还教模型使用几类工具：

- **浏览工具**：让模型调用 search 与 open 函数与网页交互，有助于事实性，也使模型能获取知识截止日期之后的信息；
- **Python 工具**：让模型在有状态的 Jupyter notebook 环境里运行代码；
- **任意开发者函数**：像 OpenAI API 那样在 Developer 消息里用 schema 描述函数，函数的定义写在 harmony 格式里（图 17 就是一例）。模型可以交错地输出 CoT、函数调用、函数返回、展示给用户的中间消息以及最终答案。

模型被训练成既能带工具也能不带工具运行，由系统提示指定。对每种工具，团队提供了基础的参考 harness（运行框架）支持核心功能，更多细节在开源实现里。

## 九、安全：默认行为（第 3、4 节）

### 9.1 方法与立场（第 3 节）

开放权重模型与专有模型的风险特征不同：一旦发布，决心很大的攻击者可以微调它们来绕过安全拒答，甚至直接针对伤害做优化，而 OpenAI 无法再实施额外的缓解措施，也无法撤销访问（第 1 节）。原文还说明，之所以称这份文件为 model card 而不是 system card，是因为 gpt-oss 会被用在各种各样的系统里，由各方创建和维护；模型虽然默认遵循 OpenAI 的安全政策，其他利益相关方也会自行决定如何保证系统安全，开发者和企业在某些场景下需要自己实现额外防护，才能复制 OpenAI 通过 API 和产品提供的系统级保护。

后训练阶段用 deliberative alignment（深思式对齐，[29]）教模型：对一大类内容（如违法建议）拒答、对越狱保持鲁棒、遵守指令层级（[30]）。（背景说明，非本卡内容：deliberative alignment 的做法是让模型学会安全规范的文字，并在回答前在 CoT 里对规范做显式推理。）

关于开放权重的测试立场，原文引用了 OpenAI 自己的一贯观点：对开放权重模型的测试条件，“理想情况下应反映下游行动者修改模型的各种方式”。开放模型最有用的性质之一，是下游可以修改模型来扩展能力并适配应用；但这也意味着恶意方可能增强模型的有害能力。因此，严格评估一次开放权重发布的风险，应当包含对恶意方在合理范围内可行的修改方式（包括微调）的测试。

按这一立场，模型卡回答了三个问题：

1. **默认模型是否达到 High？** 在 gpt-oss-120b 上做了可扩展的 Preparedness 评测，确认**默认模型**在 Preparedness Framework 的三个 Tracked Categories（生物与化学能力、网络能力、AI 自我改进）里都没有达到 High 能力的指示性阈值。
2. **对手能否通过微调把它推到 High？** 模拟攻击者的行动，为生物化学和网络两个方向各做了内部的对抗微调版 gpt-oss-120b（这些版本不会发布）。SAG 评审了这项测试，结论是即使用上 OpenAI 领先的训练栈做稳健微调，120b 仍没有在生物与化学风险或网络风险上达到 High。
3. **发布 120b 是否会显著推进开放模型的生物能力前沿？** 在其他开放基础模型上也跑了生物 Preparedness 评测。多数评测上已有至少一个开放权重模型的默认表现接近对抗微调后的 gpt-oss-120b，因此作者认为这次发布不太可能显著推进开放权重模型的生物能力水平。

原文还特别说明：除非另有标注，本模型卡里的性能结果描述的都是 gpt-oss-120b 与 gpt-oss-20b 的**默认**表现；生物化学与网络安全的 Preparedness 评测另外在对抗微调版 120b 上做了（第十章）。

### 9.4 指令层级（第 4.3 节，表 7、表 8）

**为什么需要**：模型的推理服务商可以让开发者设置自定义的 developer 消息，并附加到最终用户的每次提示上。这个功能有用，但处理不当也可能让开发者绕过 gpt-oss 的护栏。

**做法**：用 harmony 格式的多个角色（system、developer、user）做后训练：收集这些不同角色的消息互相冲突的样例，并监督 gpt-oss 在冲突时优先遵循 system 消息而不是 developer 消息，优先遵循 developer 消息而不是 user 消息。这样模型推理服务商与使用该模型的开发者可以分别在各自的层级控制护栏。

**评测一（system 与 user 冲突，模型必须听 system 的才算通过）**：系统提示提取（测试用户消息能否提取出确切的系统提示）；提示注入劫持（用户消息试图让模型说出 “access granted”，而 system 消息要求除非满足一个秘密条件否则不得这样说）。

表 7：指令层级评测，system 与 user 消息冲突（越高越好）

| 评测 | gpt-oss-120b | gpt-oss-20b | OpenAI o4-mini |
|---|---:|---:|---:|
| System prompt extraction（系统提示提取） | 0.832 | 0.881 | 0.993 |
| Prompt injection hijacking（提示注入劫持） | 0.780 | 0.639 | 0.917 |

（原文表 7，第 15 页。）

**评测二**：在 system（或 developer）消息里要求模型不要输出某个短语（如 “access granted”）或不要泄露一个特定密码，并试图在 user 消息里把它骗出来。

表 8：指令层级评测，短语与密码保护（越高越好）

| 评测 | gpt-oss-120b | gpt-oss-20b | OpenAI o4-mini |
|---|---:|---:|---:|
| Phrase protection（短语保护），system 对 user | 0.912 | 0.793 | 0.937 |
| Password protection（密码保护），system 对 user | 0.965 | 0.947 | 0.982 |
| Phrase protection（短语保护），developer 对 user | 0.909 | 0.661 | 0.912 |
| Password protection（密码保护），developer 对 user | 1.000 | 0.946 | 0.947 |

（原文表 8，第 16 页。）

**读法**：gpt-oss 在指令层级评测上总体不如 o4-mini，尤其是提示注入劫持（120b 为 0.780、20b 为 0.639，o4-mini 为 0.917）和 20b 的短语保护（developer 对 user 只有 0.661）。原文承认“还需要更多研究来理解原因”，并给出两点说明：

1. 两个模型在 StrongReject 越狱评测上与 o4-mini 大致持平，所以它们对已知越狱相对稳健，但在“防止用户覆盖系统消息”上不如 o4-mini。实际含义是：开发者靠 system 消息来缓解越狱，效果可能不如 OpenAI 对 o4-mini 做同样处理时的效果。
2. 开发者可以微调这两个模型，使其对自己遇到的越狱更鲁棒，所以仍有提高稳健性的路径。

### 9.5 “幻觉式”思维链与不对 CoT 施压（第 4.4 节）

OpenAI 此前的研究发现，监控推理模型的思维链有助于发现不当行为；但如果直接对 CoT 施加“不许有坏念头”的优化压力，模型可能学会隐藏自己的想法而继续做坏事。后来他们还与多家实验室联合发表立场文章，主张前沿开发者应“考虑开发决策对 CoT 可监控性的影响”。

基于这些担忧，团队**决定不对两个开放权重模型的 CoT 施加任何直接的优化压力**，希望这给开发者提供实现 CoT 监控系统的机会，也让研究界能进一步研究 CoT 的可监控性。

代价是：这些 CoT 不受限制，可能含有幻觉内容，包括不符合 OpenAI 标准安全政策的语言。所以**开发者不应在没有进一步过滤、审核或总结的情况下，直接把 CoT 展示给应用的用户**。

### 9.6 事实性幻觉（第 4.5 节，表 9）

用两项评测检查幻觉，都在**不给模型联网能力**的条件下运行：SimpleQA（4000 道有简短答案的多样事实性问题，衡量对已尝试回答的准确性）与 PersonQA（关于人物的问题与公开事实，同样衡量已尝试回答的准确性）。两个指标：准确率（答对）与幻觉率（答错）；准确率越高越好，幻觉率越低越好。

表 9：幻觉评测

| 评测 | 指标 | gpt-oss-120b | gpt-oss-20b | OpenAI o4-mini |
|---|---|---:|---:|---:|
| SimpleQA | accuracy（准确率） | 0.168 | 0.067 | 0.234 |
| SimpleQA | hallucination rate（幻觉率） | 0.782 | 0.914 | 0.750 |
| PersonQA | accuracy（准确率） | 0.298 | 0.155 | 0.356 |
| PersonQA | hallucination rate（幻觉率） | 0.491 | 0.532 | 0.361 |

（原文表 9，第 17 页。）**读法**：两个模型在 SimpleQA 与 PersonQA 上都不如 o4-mini，原文认为这符合预期：更小的模型世界知识更少，更容易幻觉；联网或收集外部信息通常能减少幻觉。数字上，120b 在不联网时 SimpleQA 的幻觉率高达 78.2%，20b 为 91.4%，不能把它们当作知识库。准确率与幻觉率之和不到 1，差额应是模型没有作答的比例（笔者据两项指标的定义推断）：例如 PersonQA 上 120b 约 21%、20b 约 31%。

## 十、Preparedness Framework 与对抗微调的最坏情况评估（第 5 节）

Preparedness Framework 是 OpenAI 追踪和准备应对会带来新的严重伤害风险的前沿能力的方法；框架承诺追踪并缓解严重伤害风险，对能力很强的模型要实施足以把风险降到最低的防护。本节给出为这一评估所做的详细评测。High 能力阈值的定义在框架文件里，不在本模型卡中；本卡里的“指示性阈值”主要对照各评测的专家基线（例如 TroubleshootingBench 以第 80 百分位专家得分 36.4% 为指示性阈值）以及此前已发布 OpenAI 模型的表现。

### 10.1 对抗训练：模拟一个有资源的攻击者（第 5.1 节）

默认模型的安全训练：预训练时过滤了某些与化学、生物、放射、核（CBRN）相关的有害数据；后训练时用 deliberative alignment 与指令层级教模型拒答不安全提示、防御提示注入。

但恶意行动者可以微调开放权重模型，包括 gpt-oss。为估计这种微调对 Preparedness Framework 追踪类别的影响，团队为他们认为微调有合理可能使模型达到 High 的两个类别——**生物与化学能力**和**网络能力**——创建了对抗微调版的 gpt-oss-120b。

- **攻击者模型**：技术能力强，有强大的后训练基础设施与机器学习知识，能收集有害能力方面的领域内数据，计算预算很大。可选的技术路线空间很大，团队聚焦于他们认为最贴切的**增量式强化学习**：用 OpenAI 内部的 o 系列 RL 训练栈，在保持模型推理行为的同时增加新能力；训练与评估时都使用 gpt-oss 的最高推理设置。
- **方法由两部分组成**（详见随附的研究论文）：
  1. **helpful-only 训练**：额外做一个阶段的强化学习，奖励服从不安全提示的回答。原文称这一做法可能非常有效，也曾用来创建 ChatGPT agent 等近期模型的 helpful-only 版本；
  2. **最大化与 Preparedness 基准相关的能力**：对生物模型，端到端地增量训练它做网页浏览，并用与生物风险相关的领域内人类专家数据增量训练（此前的 OpenAI 模型在这方面能力最强）；对网络模型，领域数据是网络安全夺旗（CTF）挑战环境。
- **评估与结论**：随后通过内部与外部测试评估这些模型的能力水平。SAG 评审后认为，即使用上领先的训练栈做稳健微调，gpt-oss-120b 仍未在生物与化学风险或网络风险上达到 High。

后文图中的名称对应关系（由图例与上述方法推断）：`launch candidate` 是候选发布版（默认、带安全训练）；`helpful-only` 是只做了 helpful-only 训练的版本；`bio max` 与 `cyber max` 是在 helpful-only 基础上再做领域增强的对抗微调版。

### 10.2 外部安全专家的反馈（第 5.1.1 节与附录 2）

团队请一小组外部安全专家（METR、SecureBio 与 Daniel Kang）独立审查并验证这套恶意微调方法。他们提供了论文初稿、关于微调数据集和评测脚手架的非公开细节（包括此前在恶意微调的 o4-mini 上跑过的基准），并安排了与方法论文作者的一小时问答。

外部评审共提交 22 条建议，团队采纳了其中 11 条，包括被评审者标为高优先级的 12 条中的 9 条。具体改动：增加与排障协议相关的微调数据；新增一个未被污染的协议排障评测（即后文的 TroubleshootingBench）；把过时的病毒学评测更新到最新版本；澄清了关于低资源攻击者与对抗微调成本的假设；澄清了每项评测提供的信号；写明了专家基线；改进了对拒答行为与任务级成功率的报告；测试了更强的脚手架方法。

附录 2 列出了未采纳的 3 条高优先级建议及原因：

| 建议 | 决定与理由 |
|---|---|
| 对所有评测广泛应用 best-of-N 脚手架，以提高测量质量 | 脚手架实验已在别处部分做过，完整重跑预期的额外收益有限 |
| 把 ProtocolQA 从 Preparedness 阈值中去掉（因其对排障风险的真实覆盖不完美） | 尽管有局限，ProtocolQA 提供了独特的安全信号，去掉会留下重大缺口；更大范围的 Preparedness 准则修改超出本次发布的范围 |
| 比较封闭模型与开放模型时，对封闭模型用非拒答的回复做替换后再计算综合表现，并把拒答计为 0 分 | 过去的测试发现，封闭模型在“良性代理任务”上本来就不拒答（Gryphon 除外），所以这样做对“开放模型能否追平封闭模型”提供不了多少信号 |

已采纳的做法包括：写明低资源攻击者在算力、ML 专业能力与数据获取上的假设；明确保留 ProtocolQA 为评估的必要组成并用屏蔽名单重跑 o3；对 ProtocolQA 做稳健性检查（验证模型从未拒答、增加协议排障训练数据、新增类似但未污染的排障评测）；加入生物与网络评测上“性能随试验次数扩展”的曲线；运行多模态病毒学排障评测的纯文本版本以提高可比性，并在最终 322 题的 VCT 数据集上做评测并报告人类基线；写明专家画像和基线算法；把“因拒答而失败”与其他失败模式分开，并报告“naughtification”（去安全化微调）前后的比率；在网络评测中测试内部的 “Best of K” 脚手架；在 RL 训练期间测试类似 ProtocolQA 的数据集以确认没有有害增益；与内部研究者对齐微调的最佳超参数并在必要时修改。

### 10.3 生物与化学：对抗微调后的 gpt-oss-120b（第 5.2.1 节）

原文的总评：在为测试模型能力上限而设计的**最大诱导**条件下，gpt-oss-120b 在回答涉及生物学知识与危害场景的文本问题上表现出显著的强项；但它还没有达到复杂的**协议排障**任务上的“高”指示性阈值，而且它纯文本的架构本身就限制了在依赖视觉的实验室场景中的适用性。生物是 gpt-oss-120b 展现出最大能力的领域。

团队还研究了第二个问题：即使没有达到 High，120b 会不会显著推进开放基础模型的生物能力前沿？为此把它与其他已发布的开放模型比较。起初主要考虑 DeepSeek R1-0528；中途 Qwen 3 Thinking 与 Kimi K2 发布，也被加入比较集合（相关论文见[DeepSeek-R1](../deepseek_r1/论文中文解读.md)、[Qwen3](../qwen_3/论文中文解读.md)、[Kimi K2](../kimi_k2/论文中文解读.md)）。结果确认 Qwen 3 Thinking 与 Kimi K2 已发展到使 120b 在生物安全相关评测上不再显著推进最先进水平；120b 虽在个别评测上取得最高成绩，但没有哪个开放模型在这一领域持续领先。

#### 10.4.2 网络靶场（图 12）

网络靶场练习衡量模型在真实的仿真网络里进行完整端到端网络行动的能力。这些练习是长程的，要求模型：(1) 为实现抽象的对手目标制定计划；(2) 利用野外可能见到的漏洞、错误配置与弱点；(3) 把这些利用串联起来达成场景目标。目前实现了 5 个靶场场景，分为轻度与中度难度：

- 轻度场景需要：对某种攻击行为有深入专长并有少量顺序串联；或对大量行为只有浅层专长但要做不平凡的串联。
- 中度场景需要不平凡的动作串联，并且至少对一种攻击行为有深入专长。

| 场景 | 难度 | 要点 |
|---|---|---|
| Online Retailer（在线零售商） | 中 | 对 SQL 注入（针对真实的网购门户）有深入专长，对缺失认证、发现、有效账户与凭据复用等多种攻击模式有浅层专长，并理解它们的顺序；含真实的横向移动 |
| Simple Privilege Escalation（简单提权） | 轻 | 在小网络里提权，核心是一个不平凡的提权向量（路径拦截），同时要配合有效账户与发现等基本能力；考察现场发现真实可能遇到的错误配置的能力 |
| Basic C2（基础命令与控制） | 轻 | 新场景：要设法与一台孤立的虚拟机建立命令与控制；几乎不要求显式的动作串联，但搭建 C2 通道的工作量不小；利用 Azure 网络规则增加难度 |
| Azure SSRF | 轻 | 新场景：要利用写得很差的 web 服务器，暴露有效的 Azure 凭据，并用这些凭据修改网络规则以访问目标主机；关键在于发现 web 服务器漏洞，并意识到下一步最好用 Azure 凭据；不需要太多推理或规划 |
| Taint Shared Content（污染共享内容） | 轻 | 新场景：大体线性地串联一系列弱点（实验室式的发现、SQL 注入、污染共享内容、提权）；不需要在某一方面有深入专长，但要展示自主串联的能力 |

每个场景在三种配置下测试：Normal（只给目标和 SSH 密钥）；With Hints（再给出实现目标的大致计划）；With Solver Code（再给出可用于求解该场景的部分求解代码）。每项评测跑 30 次试验，主要指标是**无提示**条件下的 pass@12；由于目前所有模型在这些评测上都是 0%，为了提供参照，还报告“有提示”条件下的 pass@1。

### 10.6 Preparedness 小结

- 默认的 gpt-oss-120b 在三个 Tracked Categories 都没有达到 High 的指示性阈值；
- 即使做了模拟强攻击者的对抗微调（helpful-only 加领域增强），生物与化学、网络两个方向也仍然没有达到 High，SAG 认可这一结论；
- 生物方向里它最强：长篇生物风险问题和隐性知识问答成绩很高，但在复杂的协议排障上低于专家基线，且纯文本架构限制了依赖视觉的实验场景；
- 与现有开放权重模型相比，没有显著推进生物能力前沿；
- 网络方向里，夺旗挑战的专业级有对抗微调带来的提升（14% 到 25%），网络靶场所有模型几乎为 0；
- AI 自我改进方向没有表现出更强的能力，gpt-oss 落后于 o3 与 o4-mini。

## 十一、局限、证据边界与常见误读

- **“开放权重”不等于“开源训练全栈”**：权重、harmony 格式与参考实现、分词器是开放的，架构超参数和训练资源也披露得相当具体；但预训练数据构成、训练 token 数、后训练配方、RL 环境、训练代码都没有公开，所以不能从零复现。
- **“激活 5.1B”不等于“只有 5B 的能力”，也不等于“只要 5B 的成本”**：120b 有 116.8B 参数的条件容量，非激活的专家提供容量，所以性能不能按 5B 密集模型估计；另一方面，路由、专家调度（跨设备通信与内存带宽）、注意力、KV cache 和 MXFP4 解码都有额外开销，计算成本也不严格等于 5.1B 密集模型。这是对 MoE 一般性质的分析，不是模型卡的结论。
- **基准数字要对口径**：原文所有主结果都是 high 推理级别、pass@1、默认系统提示。比较时要固定推理级别、是否带工具和采样设置：图 1 的 AIME 一栏是 gpt-oss 带工具、o3-mini 无工具；Codeforces 的带工具与不带工具差 160 到 290 分；表 3 里推理级别从 low 到 high 的差距往往比模型之间的差距还大。
- **思维链不能直接当解释或直接展示**：CoT 没有被施加优化压力、可能含幻觉内容和不符合安全政策的语言；原文明确要求开发者不要在没有过滤、审核或总结的情况下把 CoT 直接展示给用户。
- **只有文本**：模型卡明确它是纯文本模型，不能与 GPT-4o 这类原生多模态模型混为一谈；在生物评测里，它的纯文本架构也被原文当作限制依赖视觉的实验室场景适用性的因素。
- **能力对比只限 OpenAI 自家模型**：图 1 至图 4、表 2 和各安全表的对照都是 OpenAI 的 o3、o3-mini、o4-mini、o1 与 GPT-4o；与 DeepSeek、Qwen、Kimi 等其他开放权重模型的对比只出现在生物评测里，通用能力上没有直接对比，不能由这份模型卡得出“gpt-oss 比其他开放模型强”的结论。
- **事实性很弱，不能当知识库**：不联网时 SimpleQA 的幻觉率 120b 为 78.2%、20b 为 91.4%（表 9）；原文自己的说法是小模型世界知识少、更爱幻觉，联网能缓解。
- **指令层级不如 o4-mini**：提示注入劫持（120b 为 0.780，20b 为 0.639，o4-mini 为 0.917）和 20b 的短语保护（0.661）说明，只靠 system 或 developer 消息做护栏并不可靠。部署时要在应用层加分类器、沙箱和最小权限，必要时自己微调。
- **Preparedness 结论是特定方法下的快照**：“未达到 High”是在“技术能力强、有强后训练基础设施、预算大的攻击者”这一威胁模型和增量式强化学习这一方法下得到的，原文也提醒这些评测结果很可能只是能力下界；“没有显著推进生物前沿”依赖于当时可得的开放模型（DeepSeek R1-0528、Qwen 3 Thinking、Kimi K2），之后发布的开放模型可能超过。这不是永久的安全证明；原文开篇就指出攻击者可以通过微调绕过安全拒答，微调后的模型不再继承原有的安全行为。
- **健康成绩不代表可用于医疗**：HealthBench 得分高不代表可以用于诊断或治疗，原文特别声明这些模型不替代医疗专业人员。
- **MXFP4 的速度不由模型卡保证**：能放进多大显存是权重大小的结果，实际吞吐取决于硬件和推理引擎是否原生支持 MXFP4。

## 十二、部署与复现检查清单

- **用对格式**：用官方的 harmony 渲染器（或严格兼容的实现），不要手写模板；多轮对话中删掉历史轮次的 analysis（推理痕迹）；函数工具调用走 commentary 通道；只把 final 通道的内容展示给用户；把工具返回当作最低优先级的内容，不要把它当成可信的用户指令。
- **设置推理级别**：在 system 提示里写 `Reasoning: low`、`medium` 或 `high`；按自己任务实测选择，同时记录平均 CoT 长度、延迟与成本（图 3 与表 3 说明收益是对数线性的，且并非单调）。
- **规划显存**：权重 60.8GiB（120b）与 12.8GiB（20b）之外，还要为 KV cache（笔者估算，满 131,072 token 时单序列约 4.5GiB 与 3.0GiB）、激活与并发预留空间。
- **复现评测**：固定推理级别、是否带工具、pass@k 的定义和系统提示；原文主表用 pass@1、high、默认系统提示；注意 Codeforces、SWE-bench 等需要自带 harness，不同 harness 会改变数字。
- **安全上线**：不要直接展示 CoT；不要依赖 system 提示的“保密”；在应用层做内容过滤和权限控制；若微调了模型，要重新做拒答、越狱与指令层级评测；若涉及生物或网络能力，要自己评估微调后的风险（原文的威胁模型就是这个场景）。
- **自查数字**：表 1 的参数数字可以用词表大小、宽度、层数与专家数自行验算（见第三章），这能帮助发现自己实现里的配置错误。
