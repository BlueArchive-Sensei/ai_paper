## 1. 与 Leviathan 等人的论文是什么关系

这篇 DeepMind 工作与 *Fast Inference from Transformers via Speculative Decoding* 几乎同期提出相同核心思想：draft–verify 加 modified rejection sampling，并分别从分布式大模型系统和数学分析角度验证。本文的记号相反：target 写作 $q$，draft 写作 $p$。阅读公式时不要把两篇的 $p/q$ 角色混淆。

本文尤其值得读的是硬件解释和 Chinchilla 70B 实验：为什么一次 target scoring 多个 token 在小 batch 下接近单 token，以及 draft model 的形状和设备拓扑为什么比“参数尽量小”更重要。

## 2. 算法逐步解释

给定前缀，draft $p$ 自回归产生 $K$ 个候选。target $q$ 一次并行计算前缀后 $K+1$ 个位置的 logits。第 $t$ 个草稿 $\tilde x_t$ 的接受概率是：

$$
A(\tilde x_t)=\min\left(1,
\frac{q(\tilde x_t\mid x_{<t})}{p(\tilde x_t\mid x_{<t})}\right).
$$

若接受，继续检查下一 token；第一次拒绝时，从

$$
q'(x)=\operatorname{norm}\left([q(x)-p(x)]_+\right)
$$

采一个替代 token 并结束本轮。若 $K$ 个都接受，额外从 target 的第 $K+1$ 个位置取一个 token。

直观上，draft 先贡献 $p$ 与 $q$ 重叠的概率质量，residual 再补齐 target 比 draft 多的部分。附录定理 1 证明两部分之和恰好是 $q$，所以 draft 再弱也不改变理论输出分布，只会降低接受率并浪费计算。

## 3. Conditional scoring 为何可能几乎不变慢

论文把 Chinchilla 类 Megatron 分布式模型的 decode 时间拆成三块：

1. **Linear layers**：batch 1 时矩阵很“瘦”，瓶颈是搬权重。把一行激活变为少数几行仍可能处于 memory-bound，权重只需读一次。
2. **Attention**：已有上下文的 KV cache 远大于新增几个 token；短 $K$ 下读取旧缓存占主导。
3. **All-reduce**：张量并行中小消息常受固定通信延迟支配，激活增加少量 token 不必同比变慢。

这些条件都带有限定：$K$ 太大、batch 已饱和、位置编码或 sampling kernel 很重、KV 较短时，scoring 成本会明显增加。因此算法优势来自具体 roofline 区域，而非“Transformer 天生可免费算 $K$ 个 token”。

## 4. 为什么 draft 设计成 4B 宽浅模型

Chinchilla 70B 在 16 个 TPU v4 上约 14.1 ms/token。常规 7B 模型在 4 个 TPU 上可能约 5 ms/token，但搬到 16 个 TPU 会被通信拖慢，又不能充分利用 target 已占用的设备。作者训练 4B、仅 8 层、较宽的 draft，在同样 16 TPU 上达 1.8 ms/token。

这是一个重要系统原则：draft 的目标不是最少参数或最低 perplexity，而是在目标部署拓扑上最大化

$$
\frac{\text{acceptance gain}}{\text{draft latency + verification overhead}}.
$$

层数少可减少串行 collective 次数；适当加宽利用现有并行硬件，并保持足够预测质量。

## 5. 主实验怎么读

实验 batch size 为 1，lookahead $K=4$：

| 设置 | 下游指标：普通 / 推测 | 平均 token 时间 | 加速 |
|---|---:|---:|---:|
| XSum nucleus | ROUGE-2 0.112 / 0.114 | 14.1 → 7.52 ms | 1.92× |
| XSum greedy | ROUGE-2 0.157 / 0.156 | 14.1 → 7.00 ms | 2.01× |
| HumanEval nucleus | 45.1% / 47.0% | 14.1 → 5.73 ms | 2.46× |

指标小差异来自有限采样和数值/随机序列差异；理论主张是分布相同，不是两次运行逐样本配对相同。HumanEval 加速高，作者推测原因包括代码固定模板多、token 更短以及温度让分布更尖锐，draft/target 更易一致。

## 6. $K$ 不是越大越好

增加 $K$ 可以减少 target round 数，但有三重代价：draft 要多跑几步；越靠后的 token 必须以前面全部接受为条件；target scoring 和采样逻辑也会变重。图 1 显示 XSum nucleus 在 $K=3$ 左右最低延迟，继续加长会平台甚至回退，且生成整段的时延方差随 $K$ 增大。

在线服务尤其应看 P90/P99：较长草稿有时全收、快速前进，有时早拒、浪费整段验证，尾延迟分布可能比平均值更差。

## 7. 无损、质量与数值误差

Modified rejection sampling 在精确概率下恢复 target $q$。实际 TPU/GPU 并行图会改变浮点累加，pseudo-random seed 的消费顺序也不同，因此不能期待逐 token 相同。论文用大规模 XSum 和 HumanEval 指标验证统计等价，并把主张限定为 “within hardware numerics”。

如果工程实现使用 relaxed acceptance、typical acceptance 或为了速度跳过 residual correction，就不能再沿用本文的无损证明；必须单独评价质量偏移。

## 8. 和推理算法的边界

Speculative sampling 不是 Self-Consistency。前者为保持同一 target 分布而减少墙钟，不应提升答案正确率；后者有意从多条路径聚合，改变最终决策并增加计算。两者可组合：reasoning 系统决定生成多少条、多长轨迹，speculative engine 加速每条轨迹的 token 生成。

## 9. 复现检查表

- 固定 target、采样变换和 tokenizer；draft 的 logits 必须对应同一 token 空间。
- 在真实设备拓扑上测 draft，而非用参数量推断延迟。
- 扫描 $K$ 并报告接受率、每轮接受长度、target scoring 时间与尾延迟。
- 分 batch、context、output length、domain 报告，代码结果不能代表摘要/对话。
- 用统计质量指标验证 stochastic distribution；不要要求逐序列相等。
- 把训练和维护 draft 的成本与线上节省分开记录。
