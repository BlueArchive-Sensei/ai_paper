# 论文概要：《Serving Large Language Models on Huawei CloudMatrix384》

## 一、基本信息

- 作者：Pengfei Zuo 等（Huawei，部分作者来自 SiliconFlow）
- 公开时间：2025-06，arXiv:2506.12708
- 类型：数据中心架构与 LLM Serving 系统论文
- 研究对象：384 颗 Ascend 910 NPU 组成的 CloudMatrix384，以及面向 DeepSeek-R1 的 CloudMatrix-Infer
- 本地材料：[论文 PDF](paper.pdf) · [提取文本](paper.txt) · [中文精读](论文中文解读.md)

## 二、一句话结论

CloudMatrix384 的价值不只是“能跑 DeepSeek”：它用统一总线把 384 NPU、192 CPU 和内存资源组织成 peer-to-peer 超节点，再针对 DeepSeek-R1 的 MLA、MoE、MTP 做 P/D/C 解耦、EP320、通信融合、微批流水和 INT8；论文报告的性能很强，但结论绑定于整机、定制算子、量化和特定 SLO，不能直接外推为单卡 Ascend 与 H800 的普遍比较。

## 三、系统由什么组成

- **硬件层**：384 个 Ascend 910 NPU、192 个 Kunpeng CPU，通过 Unified Bus（UB）形成低时延、高带宽的 all-to-all 连接。
- **资源层**：计算、内存与网络可池化，不把“某块 KV 必须跟某个 GPU 绑定”作为固定前提。
- **Serving 层**：prefill、decode、cache 三类资源池独立伸缩，即 PDC disaggregation。
- **MoE 层**：decode 采用大规模 expert parallelism，论文的典型配置达到 EP320，使多数 routed expert 可一芯一专家放置。
- **算子层**：AIV-direct 通信、早量化、静态 buffer、通信流水、MLA 融合、微批流水与 MTP pipeline。

## 四、为什么 DeepSeek 特别适合这个系统

DeepSeek-V3/R1 每 token 只激活部分专家，但路由后必须进行大规模 token dispatch/combine；其 MLA 显著压缩 KV cache，却没有消除 decode 时的内存访问和小矩阵计算；MTP 又带来候选生成、验证和多图执行。CloudMatrix 把问题分别落到 UB、expert parallelism、缓存池和定制 kernel 上。

## 五、主要结果

论文在 256 个 Ascend 910 NPU 上评测 DeepSeek-R1 INT8 服务，报告：

- prefill 吞吐为 6,688 tokens/s/NPU；
- 在 TPOT < 50 ms 条件下，decode 吞吐为 1,943 tokens/s/NPU；
- 在更严格的 TPOT < 15 ms 下，仍报告 538 tokens/s/NPU；
- INT8 模型在 16 个 benchmark 上与 DeepSeek 官方 API 做准确率对照；
- context cache 复用率上升时，TTFT 显著下降；微批流水和 MTP 均有独立消融。

这些是论文配置下的系统结果，不应只截取峰值数字而忽略 prompt/output 长度、SLO、量化、EP/DP 配置和基线实现。

## 六、局限

- 硬件、CANN、算子和部署拓扑是紧密共同设计，难以拆分单一因素贡献。
- 与 H800/SGLang/DeepSeek 公布数字的比较并非完全同机、同软件、同模型格式的受控实验。
- 主要测试是 INT8 DeepSeek-R1，不能直接代表 BF16、其他模型或普通 8 卡服务器。
- 论文作者来自系统提供方，复现需要 CloudMatrix384 级别硬件与未完全公开的生产栈。
- per-NPU 指标有利于归一化，但超节点总成本、功耗、机房网络和软件运维同样重要。
