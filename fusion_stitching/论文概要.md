# FusionStitching 论文概要

## 基本信息

- 题目：*FusionStitching: Boosting Memory Intensive Computations for Deep Learning Workloads*
- 作者：Zhen Zheng 等
- 版本：arXiv:2009.10924，2020
- 原文：https://arxiv.org/abs/2009.10924
- 主题：GPU kernel fusion、XLA、内存密集算子、融合计划搜索

## 一句话结论

FusionStitching 把传统 JIT 只会做的简单 producer-consumer fusion 扩展为线程内、warp 内、block 内和独立 block 四种“拼接”方式，并用分层搜索与成本模型决定何时值得用寄存器或 shared memory 保存中间结果。

## 它解决什么问题

深度学习图里大量逐元素、归约、broadcast 和 layout 操作算术强度低。分别启动 kernel 会反复读写 HBM，并承担 CPU→GPU launch 和框架调度开销；但“能融合”不等于“应当融合”，过大的 kernel 会增加寄存器/shared-memory 压力、同步和冗余计算。

XLA 当时的融合规则偏保守，尤其难处理不同并行度的 reduction 与其 consumers。FusionStitching 的目标不是最大化融合数量，而是在更大的合法空间中选出预期延迟最低的方案。

## 核心方法

1. 用四类 composition scheme 描述不同并行结构之间如何交换中间值。
2. 先用 beam-search 式 fusion explorer 生成少量候选计划。
3. delta-evaluator 粗略估计节省的 HBM、launch 成本和新增资源成本。
4. latency-evaluator 再估算候选 kernel 的 warp 周期、occupancy、同步及冗余计算。
5. 代码生成阶段加入 shared-memory 复用、warp shuffle、循环展开和计算复用。

## 主要结果

- 对 7 个训练/推理 workload，相对 TensorFlow 最高加速 2.42×、平均 1.66×。
- 相对 XLA 最高加速 2.21×、平均 1.45×。
- memory-intensive kernel 调用数平均降到 XLA 的 38.0%，CPU 时间平均下降 41.0%。
- CRNN 案例中相关 global-memory traffic 从 667.6 MB 降到 225.8 MB。
- 论文报告生产部署每月约为 30,000 个任务节省 7,000 GPU 小时；这是特定集群与工作负载口径，不应直接外推。

## 局限

- 基于当时的 XLA、CUDA 10.2、cuDNN 7.6 和 V100/T4，结论不能直接代表现代编译栈。
- 重点是 memory-intensive 子图，GEMM/cuDNN 等 compute-intensive kernel 仍主要依赖库实现。
- 搜索与成本模型需要设备画像；资源压力估计不准会造成负优化。
- 大融合 kernel 的编译时间、调试难度和动态 shape 支持不是论文重点。

## 阅读价值

这篇适合作为“为什么 kernel fusion 不是简单合并节点”的第一篇：收益来自少写 HBM、少 launch，代价来自 occupancy、同步、冗余计算和 codegen 能力，融合决策本质上是一个带硬件约束的搜索问题。
