# Chainer 中文精读：Define-by-Run 的起点

## 1. Define-by-Run 到底改变了什么

传统 Define-and-Run：

1. 用户调用 API 构造符号 graph；
2. graph construction 阶段没有真实 tensor value；
3. 完整 graph 建好后交给 executor；
4. 多次 iteration 重复运行同一 graph。

Chainer 的 Define-by-Run：

1. Python 执行到一个 operation；
2. operation 立即计算真实 array；
3. 同时记录产生该 value 的 FunctionNode；
4. 当前 iteration 的 backward graph 随实际路径生成。

“动态”指 graph topology 可以由当前输入和 Python control flow 决定，不是说每个 tensor 的 rank 或 shape 必须变化。

## 2. 参数为什么不能只挂在计算图上

运行时 graph 生命周期通常只有一个 iteration，但 parameters 要跨 iteration 持久存在。Chainer 用 Link/Chain 把参数绑定到 object hierarchy：

- Link 持有 parameter；
- Chain 组合多个 Link；
- forward call 每次根据 Python 执行重新产生 graph；
- optimizer 遍历 object hierarchy，而不是依赖某张临时图寻找参数。

这个设计今天看似自然，却解决了动态图的关键分离：model state 是持久对象，autograd graph 是一次执行的临时记录。

## 3. 反向传播与内存生命周期

动态图会为每次 forward 创建 nodes。如果所有 inputs、outputs 和中间 array 都互相强引用，graph 很容易滞留。

Chainer 的内存策略包括：

- 从 Variable 到 creator 建反向依赖；
- 对不需要保留的中间值尽早释放；
- 通过弱引用减少 output 被 graph 长期持有；
- FunctionNode 声明 backward 真正需要保留哪些 inputs/outputs。

对普通 first-order backprop，保留最少状态；对 double backprop，则必须让 backward 计算本身可被下一层 autograd 记录。

这说明“动态图用完就释放”不是自动成立：释放时机取决于 Python reference、backward 保存集合和是否 create higher-order graph。

## 4. CuPy 为什么重要

Chainer 把 GPU array API 尽量做成 NumPy-compatible 的 CuPy：

- 用户和 library code 可在 CPU/GPU array 间保留相似表达；
- custom elementwise/reduction kernel 可按需 JIT；
- 深度学习 framework 与通用 array runtime 不必绑死。

这一思路后来可在 PyTorch 的 Tensor API、custom op 和其他 Python GPU array library 中看到类似取舍。

## 5. 动态图如何进入分布式训练

ChainerMN 没有要求所有 iteration 永远共享一个固定 graph，只要求同一次 all-reduce 中各 worker 的 parameter/gradient 结构相容。

训练程序主要增加：

- communicator；
- 包装后的 multi-node optimizer；
- dataset scatter。

gradient exchange 在 optimizer step 前发生，forward/backward 仍按 Define-by-Run 执行。

论文在 128 nodes、1024 张 P100 上训练 90-epoch ResNet-50，报告相对单卡约 70%、相对单节点约 80% scaling efficiency，平均训练时间约 897.9 秒。该结果主要说明 API 灵活性可以保留，不是现代集群的性能基线。

## 6. 应用层：为什么要有 ChainerCV

底层动态图只提供表达能力，实际视觉研究还需要：

- standardized model interface；
- pretrained weights；
- dataset、augmentation 和 evaluator；
- bbox、mask、keypoint 等约定；
- detection/segmentation 中的预后处理。

这也是“框架上层 graph”学习中容易忽略的一点：graph IR 解决计算表达，但应用生产力还依赖 state、data representation、metric 和 domain library。

## 7. 与 PyTorch autograd 的对应

| Chainer 概念 | PyTorch 中的近似对应 |
| --- | --- |
| Variable/FunctionNode | Tensor/grad_fn |
| Link/Chain | nn.Module hierarchy |
| Define-by-Run | eager execution + dynamic autograd |
| backward graph retention | retain_graph/create_graph |
| CuPy integration | ATen/CUDA Tensor 与扩展接口 |

它们不是实现一一相同，但解决的是同一组基本问题。

## 8. 常见误读

### “Define-by-Run 不需要图”

它仍需依赖图来反向传播，只是图在运行时产生，而且通常不用于提前全局优化。

### “每个 iteration 图可不同，所以分布式 worker 随便不同”

collective 和 parameter update 仍要求参与者在对应步骤上兼容。任意 divergent collective 会死锁或产生错误。

### “动态图一定比静态图慢”

动态图增加 host/dispatch 开销，但重 operator 可隐藏开销，且开发效率可能更高。性能取决于 operator 粒度、设备和是否进一步 capture/compile。

## 9. 历史边界

Chainer 已进入维护阶段；论文包含 CuPy、分布式和 CV library 等宽泛内容，不能把每项都看作 Define-by-Run 的直接结果。它今天最重要的价值是清晰展示动态图框架的原始问题分解。

## 10. 最终判断

Chainer 的贡献不是发明一张更复杂的 graph，而是改变 graph 与 Python 的主从关系：Python 程序先执行，graph 服务于本次求导。理解这一点，是区分 eager/autograd graph 与 compiler graph 的第一步。
