## 1. MoE kernel 的根本矛盾

Router 给每个 expert 的 token 数不同，而 batched GEMM 喜欢每个矩阵形状相同。常见解决办法：

1. capacity 小：截断溢出 token，损失训练信号；
2. capacity 大：padding 到相同长度，浪费算力和 activation memory；
3. dynamic capacity：不 drop，但按最大 expert load padding，最坏时更浪费。

MegaBlocks 的答案是：保留动态、负载不均的 assignment，并让 kernel 接受这种结构。

## 2. 从 expert batches 到 block-sparse matrix

假设 tokens 已按 expert 分组。每个 expert 的 FFN 第一层：

$$
Y_e=X_eW_e.
$$

$X_e$ 行数随路由变化。把所有 $X_e$ 与 $W_e$ 视作一个大 block-diagonal 稀疏乘法，就不必将每个 $X_e$ padding 到同样行数。

论文将前向/反向归纳为：

- SDD：两个 dense 输入，只产出指定 sparse blocks；
- DSD：一个 dense、一个 sparse 输入，产出 dense；
- 不同转置组合对应 forward、grad-input、grad-weight。

## 3. 为什么普通 sparse library 不够

MoE sparsity 是动态但有规则的 block sparsity。通用 sparse kernel 往往：

- block 太小，Tensor Core arithmetic intensity 不够；
- 元数据加载重；
- SDD 与 DSD 需要不同遍历顺序；
- forward 与 backward 频繁重建/转置索引。

MegaBlocks 选择适合 A100 Tensor Core 的 tile/block，并以 blocked-CSR-COO 混合格式存储：

CSR 便于按行定位 blocks，COO/额外索引支持按 expert/转置顺序访问，避免昂贵的运行时稀疏结构转换。

## 4. “Dropless”为什么影响质量

增加 capacity factor 会减少 drop、改善 validation loss，但增加 padding 计算。最低 loss 来自不 drop 的动态 capacity 方案，说明 capacity 不只是吞吐旋钮，也影响训练目标实际看到的 token。

MegaBlocks 将“是否 drop”从 kernel 约束中移除，使算法可以直接选择 dropless 语义。

## 5. 端到端训练结果

在 8×A100 80GB、64 experts、top-1、The Pile 设置下：

- 相对 Tutel dropless padding：XS/Small/Medium 为 1.38×、2.0×、4.35×；
- 相对 dense Megatron-LM 达到相同 validation loss：1.8×–2.4×；
- 相对调过 capacity factor 的 Tutel：达到相同 loss 快 1.18×–1.38×。

模型越大，padding activation memory 越显著，Tutel 可用 micro-batch 分别比 MegaBlocks 小 2×、4×、8×，因此端到端差距放大。4.35× 不只是单 kernel 快，而包含更大 micro-batch 带来的系统效率。

## 6. Kernel 结果

训练中代表 shape 上，block-sparse kernels 平均达到 cuBLAS batched GEMM 的 98.6%，标准差约 4%，范围约 91%–104%。这项对照的意义是：支持不规则 assignment 并未付出明显 dense-kernel 吞吐损失。

附录也给出 SDD/DSD CUDA 结构：

它不能证明任意 shape 都接近 cuBLAS；尤其 token 很少、block occupancy 低或新架构 Tensor Core tile 改变时需重新调优。

## 7. 这篇论文没有消除什么

- router 仍可能负载不均或塌缩；
- token permutation/unpermutation 仍存在；
- expert parallel 的 all-to-all 仍存在；
- total expert weights 仍占显存；
- block 末尾仍可能有粒度内浪费；
- inference 的小 batch/decode shape 与训练不同。

“Dropless”只表示不因 capacity constraint 丢 token。

## 8. 与 Switch Transformer 的关系

Switch 用 fixed capacity 让专家矩阵规则化，系统容易实现，却把 overflow 变成算法语义；MegaBlocks 用 block-sparse kernel 恢复动态 batch。

关系可以概括为：

- 固定 capacity：规则 batched GEMM，但需要 dropping 或 padding；
- block sparse：保留动态 expert batch，但需要更复杂的 kernel 与 metadata。

## 9. 常见误读

### “Sparse 一定比 dense 慢”

非结构化细粒度 sparsity 常如此；MegaBlocks 利用的是较大规则 blocks 和已知 expert structure。

### “98.6% cuBLAS 意味着端到端只慢 1.4%”

该数字只针对核心 block-sparse matmul。端到端还有 routing、permutation、通信和其他层。

### “4.35× 都来自 kernel”

大模型上的主要放大因素还包括 padding activation 导致 Tutel micro-batch 更小。

## 10. 复现检查点

- 固定 A100/CUDA/CUTLASS 版本、block size 和 mixed precision。
- 同时 benchmark SDD/DSD 的 forward 与两类 backward。
- 报告 token/expert 分布、空 expert 与尾块利用率。
- 将 permutation、metadata construction、all-to-all 纳入端到端。
- 比较时保持最终 loss 或训练 token 数一致，不能只比 steps/s。
- 记录 micro-batch 是否因内存改变。

## 12. 最终判断

MegaBlocks 是 MoE kernel 的代表作，因为它没有把不规则性藏在 padding 里，而是把模型真实的动态结构显式映射为 block sparsity。其核心启示是：当硬件友好形状要求迫使算法丢数据时，应考虑改变 kernel abstraction，而不只是继续调 capacity factor。
