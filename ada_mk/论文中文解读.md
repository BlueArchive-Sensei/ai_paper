## 1. 为什么 Ada GPU 需要不同 MegaKernel

Hopper/Blackwell 上的 MegaKernel 可依赖更大 shared memory、TMA 和新 tensor instructions。L20 属于 Ada（compute capability 8.9）：

- 无 TMA；
- SMEM 更紧；
- 需要软件 pipeline/显式 PTX 搬运；
- 小 batch、毫秒级 latency 对 branch/queue overhead 更敏感。

论文 profile Qwen3-1.7B/TensorRT-LLM，称 decode 的 launch overhead 约占端到端 14.6%。这只是特定模型、L20、配置的观察。

## 2. 总体架构

### Phase I：离线

- 将 decoder 与 LM head 降为细粒度 DAG；
- 分析依赖、alias 和资源；
- 搜索 warp roles、pipeline、buffer pages；
- 固化成无 runtime 分支的执行序列。

### Phase II：在线

- TensorRT-LLM 处理 prefill；
- plugin 在 decode 使用 MegaKernel；
- 复用 TensorRT-LLM 的 request/runtime 生态。

这是一种 phase-adaptive 设计：prefill 计算大、launch 相对不重要；decode 小算子多，更值得 megakernelize。

## 3. Shared memory 模型

资源估计同时看：

- GPU：SMEM 容量、warp/SM、指令能力；
- 模型：hidden size、quant scales、KV shape；
- workload：batch、sequence、量化格式。

K-dimension splitting 将一个大 GEMM/weight tile 切成更小阶段，论文称峰值 SMEM 降约 50%；跨 operator page reuse 让生命周期不重叠的 instructions、semaphores、scratch 共用空间。

## 4. DAG 搜索

Compiler 从 MLIR/低级 primitive 建立 read-after-write 等依赖，并搜索：

- Loader/Consumer/Storer 等 warp role 数；
- stage 数与双/多缓冲；
- 哪些 weights 提前 prefetch；
- shared-memory page lifetime；
- reduction 与后继 compute 的 overlap。

与通用 runtime scheduler 不同，Ada-MK 假设部署的 model、quantization、batch 范围固定，因此最佳路径可离线确定。它用编译成本换在线 branch-free latency。

## 5. Pipeline 细节

论文通过：

- RMSNorm/weight 的异步预取；
- Consumer warps 重分配；
- cross-block reduction 与 compute 对齐；
- padding I/O 消除

平衡各 pipeline stage。核心目标不是单个 GEMM 峰值，而是让 persistent decoder 的 producer/consumer 不互相饿死。

## 6. 为什么嵌入 TensorRT-LLM

完全替换成熟 engine 会丢失模型支持、KV cache、serving、量化与 prefill 优化。Ada-MK 采用 hierarchical replacement：

- 高层仍由 TensorRT-LLM 调用；
- 只把 decode 主路径替换为 plugin；
- unsupported/非甜点 workload 保留原生路径。

这是比“新系统全栈对打”更现实的落地方式，也使它直接回答 TensorRT-LLM 用户如何引入 MegaKernel。

## 7. 实验结果

环境是单 L20 48 GB、CUDA 12.2，两个约 1.5B–1.7B 的 GPTQ-W4A16 Qwen 模型。

固定 input 64/output 12：

- Qwen3 相对 vanilla TensorRT-LLM 全 batch >10%，batch 1 最高 23.6%；
- Qwen2.5 提升约 6.7%–15.6%。

CSL：

- batch 1–8 Ada-MK 最快；
- batch 16 被 vLLM 超过 3.5%，与 SGLang 近似。

HumanEval：

- batch 16 仍比 TensorRT-LLM 高 19.5%；
- 相对 vLLM/SGLang 只领先 1.6%/3.5%。

这表明 MegaKernel 最稳定的甜点区是小 batch decode；并发、长 context 变大后，request scheduling 和 KV management 的系统优势会重新主导。

## 8. 证据边界

- 两个模型规模相近，不能证明跨大模型泛化；
- 只有单 Ada GPU，没有 Hopper/Blackwell 或 multi-GPU；
- 全部 GPTQ-W4A16，不能外推 BF16/FP8/NVFP4；
- offline simultaneous batch 排除了在线 arrival/scheduler 差异；
- “工业部署”是作者陈述，没有公开 trace 或长期 SLO 数据。

## 9. 常见误读

### “编译期固定路径比动态调度总好”

只在配置稳定且 runtime variability 有界时。MoE 路由、continuous batching 或 ragged shape 可能需要动态机制。

### “MegaKernel 可以替代 TensorRT-LLM”

论文反而选择嵌入 TensorRT-LLM，说明 engine-level scheduling、KV 与模型生态仍必要。

### “23.6% 是所有 TRT-LLM workload 的收益”

它对应 Qwen3-1.7B、L20、W4A16、batch 1、64/12 的特定点。

## 10. 复现检查点

- 锁定 TensorRT-LLM v1.1.0rc5、vLLM/SGLang 版本与容器。
- 固定量化校准与输出正确性。
- 报告 prefill/decode 分别用何路径。
- 测 TTFT、TPOT、throughput、P99，而不只 tokens/s。
- 把 offline search/compile time 与 cache invalidation 记录下来。
- 对 batch/sequence/model change 验证是否重新生成 MegaKernel。

## 11. 最终判断

Ada-MK 最有启发性的地方是“异构共存”：让 TensorRT-LLM 负责它擅长的完整 runtime 和 prefill，让编译期专用 MegaKernel 攻击小 batch decode 的固定开销。它的结果很有针对性，也因此必须严格限定在 L20、小模型、W4A16 的证据范围内。
