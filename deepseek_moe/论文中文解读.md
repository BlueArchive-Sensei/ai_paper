## 一、核心问题：普通 MoE 的专家并不一定“专业”

标准 top-k MoE 把每个 token 路由到少量大 FFN。它省计算，但有两个结构性问题：每个大 expert 必须同时容纳许多类型知识；多个 expert 又可能重复学习通用模式。参数很多，不代表条件计算被有效利用。

DeepSeekMoE 的思路是把“一个粗专家”改成“多个可组合的小专家”，并显式分离公共知识。论文于 2024 年 1 月公开，arXiv:2401.06066。本地保存 [PDF](paper.pdf)、[文本](paper.txt) 与 [概要](论文概要.md)。

## 二、Figure 2：两步改造

假设基线有 `N` 个专家，每个 token 激活 `K` 个。细粒度分割把每个 FFN 切为 `m` 份，得到 `mN` 个专家，并激活 `mK` 个。每个小 expert 约为原 expert 的 `1/m`，所以单 token 激活的 FFN 参数/计算保持近似不变。

变化在组合数。基线只有从 `N` 中选 `K` 的组合；细分后从 `mN` 中选 `mK`，路由器能用多个小模块拼出更具体的知识组合。它类似把少量“大科室”拆成更多“专科小组”。

shared expert isolation 再固定一部分 expert 对所有 token 生效。公共语言结构、常识模式不必在每个 routed expert 内复制；路由专家可以把容量留给差异化知识。

## 三、负载均衡仍是必要条件

MoE 的理论计算节省只有在专家负载可控时才能兑现。路由塌缩会使热点 expert 过载，产生 token dropping、padding 或设备空闲。论文沿用 auxiliary loss 约束 importance 与 load，并在训练中设置 capacity。

这也说明 DeepSeekMoE 论文与 V3 的关系：V3 没有抛弃这套专家结构，而是进一步把“依赖辅助损失的平衡”改为调整 expert bias 的 auxiliary-loss-free 策略，减少质量与平衡目标的冲突。

## 四、验证实验怎样证明设计有效

论文先在 2B 级模型做受控比较，避免直接拿不同数据、不同训练预算的大模型排行榜来证明架构。主要比较对象包括同计算的 GShard、更多 expert 参数的 GShard×1.5，以及等总参数 dense 模型。

结果支持两个层次的结论：

- 与相近激活计算的传统 MoE 相比，细粒度 + shared expert 更好；
- 与等总参数 dense 上界仍有差距，但差距缩小，说明更多非激活参数确实转化成了能力。

## 五、消融与“专家可替代性”

论文分别去掉细粒度分割和 shared expert，观察验证 loss/benchmark 下降；两项都有效，组合最好。另一个有意思的实验是禁用 top routed experts：如果关闭最常用专家后性能骤降，表示知识过度集中；DeepSeekMoE 相对更稳，作者据此认为细粒度组合提高了替代性。

不过“更稳”不等于专家已经完全可解释。一个 expert 激活于哪些 token、承载何种知识仍可能高度混合；论文没有像 mechanistic interpretability 工作那样给每个 expert 做因果语义验证。

## 六、16B 与 145B 的扩展

DeepSeekMoE 16B 约有 2.8B 激活参数，论文报告总体表现接近 LLaMA2 7B，而计算量约为后者 39.6%。145B 预实验又与 DeepSeek 67B dense 做比较，显示更低激活计算下的接近表现。

这里“计算量”主要指模型 FLOPs。实际 wall-clock 还需加入：

```text
T = T_GEMM + T_route + T_dispatch/combine
  + T_all-to-all + T_padding/imbalance + T_framework
```

如果网络较慢或 batch 太小，MoE 的 FLOPs 优势可能不能变成同比 latency 优势。这正是后续 DeepSeek-V3 的通信优化，以及 CloudMatrix384 的大规模 EP/UB 设计要解决的问题。

## 七、这篇论文在 DeepSeek 技术树中的位置

```text
DeepSeekMoE
  ├─ fine-grained routed experts
  └─ shared expert isolation
           ↓
DeepSeek-V2
  ├─ 延续 DeepSeekMoE
  └─ 加入 MLA，降低 KV cache
           ↓
DeepSeek-V3
  ├─ auxiliary-loss-free load balancing
  ├─ node-limited routing / 通信共设计
  └─ MTP + DualPipe + FP8
```

因此阅读 V3 时，不应把所有创新都归到 V3；专家结构的核心来源就是本文。

## 八、实践启示

- 设计 MoE 时同时报告 total parameters、active parameters、top-k 与专家粒度。
- 只看 token-level FLOPs 不够，至少同时测 all-to-all bytes、负载分布、drop rate 和端到端吞吐。
- shared expert 是容量分工，不等价于 residual dense FFN；它也消耗每 token 固定计算。
- 细粒度增加组合能力，也增加路由和通信对象数量，最优配置取决于网络与 kernel。
