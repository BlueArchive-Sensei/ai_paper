## 1. 资料性质、版本与一句话结论

## 3. Dynamo 捕获的不是“整个 Python 世界”

文档的说法：`torch.compile` 的前端 Dynamo 是一个**自定义的 Python 字节码解释器**，设计目标是在保留 Python 全部灵活性的前提下做 PyTorch 程序的图编译。给定一个要编译的函数，Dynamo 解释它的 Python 字节码，把其中的 PyTorch 运算序列抽取成 **1 个或多个 FX 图**，再交给后端进一步优化。

对一个 frame（函数调用），Dynamo 产出三样东西：

1. **一张或多张 FX 图**：捕获了 Python 函数（及其嵌套函数调用）语义的、线性的运算序列；
2. **残余字节码（residual bytecode）**：可作为原函数 `f` 的直接替代；它负责取得图所需的额外输入、把它们传给图，并包含**无法优化的 Python 副作用**（文档例子里是列表的 `append`）；
3. **guards**：一组条件，说明图和字节码**在什么情况下有效**。文档强调：除非另行指定，Dynamo 产生的图会**按输入张量的 shape 做专门化**。

文档在这里引用了一张总览图（`dynamo_summary_diagram.png`）并以图中的函数 `f` 为例说明上面三样产物；这张图片没有保存在快照里，所以本文只转述文档的文字描述，不描述图的内容。

因此 compiled function **不是简单地换成一个单一的图执行器**：它仍然可能在各个图区域之间执行 Python。与论文的对应（笔者补充）：这里的“残余字节码”就是 [PyTorch 2 论文](../pytorch_2/论文中文解读.md)图 1 里的“Transformed PyCodeObject（non-torch.* bits）”，“guards”就是该论文第 3.3 节的 guard 函数，“FX 图”就是被送去编译的 `torch.*` 部分。

## 4. Graph break

### 4.1 定义与默认行为

Dynamo 追踪你的代码，尝试把 PyTorch 代码捕获成**单张**由 PyTorch 运算符构成的计算图（FX 图）；但这并不总是可能。遇到无法追踪的代码时会发生 **graph break**。默认的 `torch.compile` 设置下，graph break 的过程是：

1. 编译到目前为止已经确定的 FX 图；
2. 用普通 Python 运行无法追踪的代码；
3. 在这段代码之后，用一张新的 FX 图恢复追踪。

文档把 graph break 描述成**一个特性**：它让 Dynamo 能在任意 Python 代码上运行，并从中划出一个个可以独立优化的函数式子图。但 graph break 也可能带来意料之外的变慢；如果没有得到预期的加速，文档建议检查并消除 graph break。

### 4.2 何处会发生

文档列出 graph break 可能出现在：

| 类别 | 例子 |
|---|---|
| 数据依赖的 `if` 语句 | 条件取决于张量的值 |
| 许多 Python 内建函数 | - |
| C 函数 | - |

### 4.3 文档的例子：`torch.save`

下面的例子因为调用了不被支持的运算 `torch.save` 而发生 graph break：

```python
@torch.compile
def f(x):
   y = x ** 2  / 2
   torch.save(y, "foo.pt")  # torch.save is an unsupported operation
   z = y ** 3 / 6
   return z

x = torch.randn(3)
print(f(x))
```

文档给出 `torch.compile(f)(x)` 的**大致语义**：

```python
def compiled_f_semantics(x):
   y = torch.compile(g, fullgraph=True)(x)
   torch.save(y, "foo.pt")
   z = torch.compile(h, fullgraph=True)(x)
   return z

def g(x):
    return x ** 2  / 2

def h(x):
    return y ** 3 / 6
```

**逐行解释**：

- 原函数被 `torch.save` 切成两段：`torch.save` 之前（`y = x ** 2 / 2`）和之后（`z = y ** 3 / 6`）；
- `g` 是前一段，被编译成一张独立的图（`fullgraph=True` 表示这一段必须是完整的单张图，不再允许 graph break）；
- 中间的 `torch.save(y, "foo.pt")` 在**普通 Python** 里执行；
- `h` 是后一段，被编译成第二张图；
- 文档这段近似语义代码有笔误：`h` 的函数体用了未定义的 `y`，调用处也传了 `x`；按语义应是 `h(y)`、函数体对其参数做 `** 3 / 6`。这里照文档原样转录。
- **读法**：一次调用里有**两次**图执行，中间夹着一次 Python 执行；两段图之间的中间值 `y` 要落地为真实张量，不能在两张图之间融合。

### 4.4 graph break 的代价与相关选项（笔者补充）

文档只说 graph break 可能导致变慢、并阻碍后端优化机会。笔者按一般认识补充几点具体代价（快照里没有这段）：多次图调用与调度；丢失跨 break 的融合；Python 开销回来；中间张量必须物化；调试和图数量更复杂。`fullgraph=True` 把 graph break 变成错误，适合发现问题，不表示所有生产负载都必须是一张图；文档里这个选项只出现在上面的例子和目录页里（`Use fullgraph=True to Identify and Eliminate Graph Breaks`）。

## 5. Guards 与重编译

### 5.1 Guards

`torch.compile` 在追踪代码的过程中会对运行时值做一些**假设**。追踪时为这些假设生成 **guards**，即对这些假设的运行时检查；之后每次调用已编译函数时都会运行 guards，来判断是否可以复用先前编译的代码。文档给出的运行时检查例子：常量值、类型和对象 ID。

因为 guards 在**每次调用**时都要运行，它们会带来每次调用的额外开销；如果这个开销对你的模型很显著，文档建议参阅 Reducing Guard Overhead（本快照未包含该页）。

文档给出的例子：

```python
@torch.compile
def fn(x):
    return x + 1

print(fn(torch.ones(3, 3)))
```

文档说明这个例子里生成的 `TENSOR_MATCH` guard 检查输入的类型、设备、dtype、shape 等。（生成的 guards 的实际打印输出没有保存在快照里。）

笔者补充：PyTorch 2 论文说 guard 共有 30 种类型，检查内容包括 `torch.Tensor` 属性、Python 类型、常量特化、属性、dict/list/tuple、`nn.Module` 实例和全局 PyTorch 状态，并且 guard 系统横跨 TorchDynamo、AOTAutograd 和 TorchInductor 三层。

### 5.2 重编译（recompilation）

如果 guards 对**所有**先前已编译的代码实例都失败，`torch.compile` 就必须**重编译**这个函数，即把原代码重新追踪一遍。文档的例子：

```python
@torch.compile
def fn(x):
    return x + 1

print(fn(torch.ones(3, 3)))
print(fn(torch.ones(4, 4)))
```

**读法**：第一次调用用 $3\times3$ 张量，编译时按静态 shape 生成 guard；第二次用 $4\times4$ 张量，检查张量参数 shape 的 guard 失败，所以需要重编译（文档原话：“recompilation is necessary because the guard checking the tensor argument's shape failed”）。重编译会增加总的编译时间；降低这类成本的办法见 Dealing with Recompilations 和 Reducing Compile Time（本快照未包含）。

### 5.3 复用与失效的规则

把上面两小节合起来（笔者整理，来自文档的措辞）：

- 某个已缓存版本的 guards **全部通过**：复用该版本；
- **所有**已缓存版本都失败：重新追踪并编译；
- 目录里有“Changing the Cache Size Limit”“Hitting a Recompilation Limit”之类的小节，说明版本数或重编译次数有上限，达到上限后的行为在本快照里没有正文；
- guard 不只是安全检查，也是**专门化的边界**：假设越具体，优化器得到的信息越多，但输入变化时复用率越低。

## 6. 四种 graph 不要混用（笔者整理）

| Graph | 产生方式 | 包含内容 | 生命周期与用途 |
|---|---|---|---|
| Autograd 图 | eager 逐算子记录 | 反向依赖 | 本次训练迭代 |
| FX 符号图 | Proxy 追踪 | 选定路径上的高层调用 | 图变换 |
| Dynamo 的 FX 图 | 字节码捕获 | 可编译的张量区域 | `torch.compile` 的前端 |
| ExportedProgram 的图 | export 追踪加约束 | 函数式的、ATen 风格的完整图 | 提前编译与部署 |

AOTAutograd 还会把训练计算提前捕获成前向、反向图；它与 eager autograd 图的产生时机和用途不同（见 [PyTorch 2 论文解读](../pytorch_2/论文中文解读.md)第 3.9 节）。这张表里的“Autograd 图”“FX 符号图”不是这四个页面的内容，是笔者对本仓库这条阅读线的归纳（见 [PyTorch 2019 论文](../pytorch_imperative/论文中文解读.md)、[torch.fx](../torch_fx/论文中文解读.md)）。

## 7. torch.export 的两种 tracing

### 7.1 基础

`torch.export.export()` 通过在“示例（example）”输入上追踪执行，记录追踪路径上观察到的 PyTorch 运算和条件，得到一张表示模型的图；这张图可以在不同输入上运行，只要它们满足**同样的条件**。基本输出是**一张**带元数据的 PyTorch 运算图（具体格式见 export IR 规范）。

### 7.2 strict 与 non-strict

`torch.export.export()` 提供两种追踪模式：

| 模式 | 怎么追踪 | 好处与风险 |
|---|---|---|
| non-strict（非严格） | 用**普通 Python 解释器**追踪：代码像 eager 一样原样执行，不同的是所有张量被换成 **fake 张量**（只有 shape 等元数据、没有数据），并包在 **Proxy** 对象里，把对它们的所有运算记录进图；同时捕获保护生成代码正确性的**张量 shape 条件** | 对多数模型，shape 条件足以保证可靠性；不会遇到 Dynamo 不支持的 Python 特性 |
| strict（严格） | 先用 **TorchDynamo**（Python 字节码分析引擎）追踪：Dynamo 并不真正执行你的 Python 代码，而是符号地分析它并据此建图 | 这种分析能提供 Python 层面的额外安全保证（超出 non-strict 捕获 shape 条件的部分）；但并非所有 Python 特性都被这种分析支持 |

文档的建议：虽然**当前默认是 strict**，但**强烈推荐 non-strict，它很快会成为默认**。理由是：对大多数模型，shape 条件足以保证可靠性，Python 层面的额外保证没有影响；同时在 TorchDynamo 里碰到不支持的 Python 特性是不必要的风险。文档后面的讨论一律假定 non-strict 追踪，并且假定所有 Python 特性都被支持。

## 8. Static value 与 dynamic value

### 8.1 定义

- **静态值（static value）**：在导出时就固定、导出程序的多次执行之间**不能改变**的值。追踪遇到它时把它当作常量**写死**进图。当一个运算（如 `x + y`）的所有输入都是静态的，运算的结果直接写进图，运算本身不会出现（被“常量折叠”）。当一个值被写死进图，就说这张图**被专门化**到该值。
- **动态值（dynamic value）**：可以逐次运行变化的值，行为就像“正常”的函数参数：可以传不同的输入并期待函数做对的事。

文档的例子：

```python
import torch

class MyMod(torch.nn.Module):
    def forward(self, x, y):
        z = y + 7
        return x + z

m = torch.export.export(MyMod(), (torch.randn(1), 3))
print(m.graph_module.code)

"""
def forward(self, arg0_1, arg1_1):
    add = torch.ops.aten.add.Tensor(arg0_1, 10);  arg0_1 = None
    return (add,)

"""
```

**逐行解释**：`y` 在追踪时被给定为 `3`，它是 Python 整数，被当作**静态值**；`z = y + 7` 的两个操作数都是静态的，所以直接算出 `10` 并**烧进图里**，图里只剩 `x + 10` 这一次加法，`arg1_1`（对应 `y`）在图中没有任何使用。含义是：导出后给 `y` 传别的值会出错（见 8.3）。

### 8.2 哪些值是静态的、哪些是动态的

是否静态取决于类型：

| 类型 | 规则 |
|---|---|
| 张量数据 | 动态 |
| 张量 shape | 系统可以当作静态或动态。**默认所有输入张量的 shape 都是静态的**；用户可以对任何输入张量指定动态 shape 来覆盖；属于模块状态的张量（参数和 buffer）**总是**静态 shape |
| 其他张量元数据（如 `device`、`dtype`） | 静态 |
| Python 原始类型（`int`、`float`、`bool`、`str`、`None`） | 静态；某些原始类型有动态变体（`SymInt`、`SymFloat`、`SymBool`），通常用户不必处理；用户可以通过指定动态 shape 把整数输入指定为动态 |
| Python 标准容器（`list`、`tuple`、`dict`、`namedtuple`） | **结构**静态（`list`、`tuple` 的长度，`dict`、`namedtuple` 的键序列）；其中的元素递归地套用这些规则（基本就是 PyTree 方案），叶子是张量或原始类型 |
| 其他类（含数据类 dataclass） | 可注册为 PyTree，注册后与标准容器遵循同样的规则 |

### 8.3 输入类型

输入按上述类型被当作静态或动态：

- **静态输入**会被写死进图，运行时传不同的值会导致**错误**（这主要是原始类型的值）；
- **动态输入**行为像“正常”的函数输入（主要是张量类型的值）。

默认情况下，程序输入可以用的类型：张量；Python 原始类型；Python 标准容器。

**自定义输入类型（PyTree）**：可以定义自己的类并作为输入类型，但需要把它注册为 PyTree。文档的例子是用一个工具注册数据类：

```python
@dataclass
class Input:
    f: torch.Tensor
    p: torch.Tensor

import torch.utils._pytree as pytree
pytree.register_dataclass(Input)

class M(torch.nn.Module):
    def forward(self, x: Input):
        return x.f + 1

torch.export.export(M(), (Input(f=torch.ones(10, 4), p=torch.zeros(10, 4)),))
```

**读法**：`Input` 数据类含两个张量字段；`pytree.register_dataclass(Input)` 让导出系统能把它拆成叶子（两个张量）并还原；之后 `x.f + 1` 就像普通输入一样被追踪。

**可选输入**：对没有传入的可选输入，`torch.export.export()` 会**专门化到它们的默认值**。结果是导出程序要求用户显式传入所有参数，丢失默认值行为。文档的例子：

```python

        if y is not None:
            return y * x
        return x + x

# Optional input is passed in

print(ep)

        def forward(self, x: "f32[3, 3]", y: "f32[3, 3]"):
            # File: /data/users/angelayi/pytorch/moo.py:15 in forward, code: return y * x
            mul: "f32[3, 3]" = torch.ops.aten.mul.Tensor(y, x);  y = x = None
            return (mul,)
"""

# Optional input is not passed in
ep = torch.export.export(M(), (torch.randn(3, 3),))
print(ep)
"""
ExportedProgram:
    class GraphModule(torch.nn.Module):
        def forward(self, x: "f32[3, 3]", y):
            # File: /data/users/angelayi/pytorch/moo.py:16 in forward, code: return x + x
            add: "f32[3, 3]" = torch.ops.aten.add.Tensor(x, x);  x = None
            return (add,)
"""
```

**读法**：两次导出得到两张**不同**的图：传入 `y` 时是 `y * x`，没传 `y` 时是 `x + x`，而且后者的签名里 `y` 仍保留着一个占位参数但图中不使用——`y is not None` 这个条件在导出时就被专门化了（`y` 作为 `None` 是静态的）。所以“输入是函数参数”不代表它一定成为图的运行时输入。

## 9. 控制流：static、shape-dependent 与 data-dependent

`torch.export.export()` 支持控制流；行为取决于你分支所依据的值是静态的还是动态的。

### 9.1 静态控制流

对静态值的 Python 控制流被**透明地支持**（静态值包含静态 shape，所以对静态 shape 的控制流也属此类）。因为静态值被“烧进”图，导出的图**永远看不到**对静态值的控制流：

- `if` 语句：继续追踪导出时走过的那个分支，另一侧不进入图；
- `for`、`while` 语句：通过**展开循环**继续追踪。

### 9.2 动态控制流：依赖 shape 与依赖数据

当控制流涉及的值是动态的，它可能依赖动态 shape，也可能依赖动态数据。因为编译器追踪时拿到的是 shape 信息而不是数据，这两种情形对编程模型的含义不同。

**（1）依赖动态 shape 的控制流（shape-dependent）**：当控制流涉及的值是动态 shape 时，多数情况下追踪期间我们也知道这个动态 shape 的具体值（编译器怎样跟踪这个信息见第 10 节）。这时我们用该具体值把条件求值为 `True` 或 `False` 并继续追踪，同时**额外发出一条与刚求值的条件对应的 guard**。否则，控制流就被视为依赖数据（data-dependent）：我们无法把条件求值为 `True` 或 `False`，所以无法继续追踪，必须在导出时**报错**。

**（2）依赖动态数据的控制流（data-dependent）**：这种控制流是支持的，但必须用 PyTorch 的**显式算子**才能继续追踪；对动态值使用 Python 控制流语句是**不允许**的，因为编译器无法求值继续追踪所需的条件，导出时只能报错。文档提供了表达一般条件和循环的算子，如 `torch.cond`、`torch.map`；只有当你真的需要数据依赖的控制流时才需要用它们。

文档的例子：对数据依赖的条件 `x.sum() > 0`（`x` 是输入张量）的 `if`，用 `torch.cond` 改写：

```python
class M_old(torch.nn.Module):
    def forward(self, x):
        if x.sum() > 0:
            return x.sin()
        else:
            return x.cos()

class M_new(torch.nn.Module):
    def forward(self, x):
        return torch.cond(
            pred=x.sum() > 0,
            true_fn=lambda x: x.sin(),
            false_fn=lambda x: x.cos(),
            operands=(x,),
        )
```

**读法**：`M_old` 的条件取决于张量的**值**（`x.sum()` 的符号），fake 张量没有数据，追踪器无法选分支，导出会报错；`M_new` 把两个分支都作为函数传给 `torch.cond`，**两个分支都会被追踪**，图里保留一个条件算子，运行时再按真实数据选择。

**（3）数据依赖的动态 shape 这一特例**：典型情形是某个中间张量的 shape 取决于输入数据而不是输入 shape（所以不是 shape-dependent）。此时不必用控制流算子，可以提供一个**断言**来决定条件是 `True` 还是 `False`；有了断言就能继续追踪，并如前发出 guard。文档提供表达动态 shape 断言的算子，如 `torch._check`；只有在对数据依赖的动态 shape 做控制流时才需要用。文档的例子：对条件 `nz.shape[0] > 0` 的 `if`，其中 `nz` 是 `torch.nonzero()` 的结果（输出 shape 依赖输入数据）：

```python
class M_old(torch.nn.Module):
    def forward(self, x):
        nz = x.nonzero()
        if nz.shape[0] > 0:
            return x.sin()
        else:
            return x.cos()

class M_new(torch.nn.Module):
    def forward(self, x):
        nz = x.nonzero()
        torch._check(nz.shape[0] > 0)
        if nz.shape[0] > 0:
            return x.sin()
        else:
            return x.cos()
```

**读法**：`nz.shape[0]`（非零元素个数）是 **unbacked** 的动态 shape（见第 10 节），不能直接用于 `if`；`M_new` 里 `torch._check(nz.shape[0] > 0)` 断言“个数大于 0”，等于**替追踪器决定走 `x.sin()` 这个分支**，之后的 `if` 就能求值；这个断言会作为导出程序里的运行时检查保留（见第 11 节）。

这解释了为什么“PyTorch eager 能运行”不等于“export 能自动得到完整的控制流图”。

## 10. Backed 与 unbacked symbol

### 10.1 符号 shape 的基础

追踪期间，动态张量 shape 以及对它们的条件被编码成**符号表达式**（相对地，静态张量 shape 以及对它们的条件只是普通的 `int` 和 `bool` 值）：

- **符号（symbol）** 像变量，描述一个动态张量 shape；
- 随着追踪推进，中间张量的 shape 可以用更一般的表达式描述，通常涉及整数算术运算符，因为对大多数 PyTorch 运算符，输出张量的 shape 可以写成输入张量 shape 的函数；例如 `torch.cat()` 的输出 shape 是各输入 shape 之和；
- 遇到程序中的控制流时，会创建**布尔表达式**（通常涉及关系运算符），描述追踪路径上的条件；这些表达式被求值来决定追踪走哪条路径，并被记录在一个 **shape environment（shape 环境）** 里，用来保护被追踪路径的正确性，并用于求值之后创建的表达式。

### 10.2 算子的 fake 实现

追踪时程序是用没有数据的 fake 张量执行的，一般不能对 fake 张量调用 PyTorch 算子的真实实现。因此每个算子需要一个额外的 **fake（又称 meta）实现**：输入输出都是 fake 张量，在 shape 及 fake 张量携带的其他元数据方面与真实实现的行为一致。文档以 `torch.index_select()` 为例：

```python
def meta_index_select(self, dim, index):
    result_size = list(self.size())
    if self.dim() > 0:
        result_size[dim] = index.numel()
    return self.new_empty(result_size)
```

**逐行解释**：`result_size = list(self.size())` 先取输入的 shape；若输入不是标量，则把 `dim` 这一维的大小换成 `index` 的元素个数——只用输入的 shape 算出输出的 shape；`self.new_empty(result_size)` 返回一个只有 shape、**没有有意义数据**的空张量。这就是 fake 实现：忽略输入数据，只做 shape 推导。

### 10.3 Backed 与 unbacked

shape 的传播用算子的 fake 实现完成。理解动态 shape 传播的关键是 **backed（有后备）** 与 **unbacked（无后备）** 动态 shape 的区别：**前者我们知道具体值，后者不知道**。传播规则：

- 表示输入的张量的 shape 可以是静态或动态。动态时用符号描述，并且这些符号是 **backed** 的，因为导出时用户提供的“真实”示例输入也让我们知道它们的具体值；
- 算子的输出 shape 由它的 fake 实现计算，要么静态要么动态，动态时一般用符号表达式描述。并且：
  - 如果输出 shape 只依赖输入 shape，那么当输入 shape 都是静态或 backed 动态时，输出要么静态要么 backed 动态；
  - 另一方面，如果输出 shape 依赖输入**数据**，它必然是动态的，而且因为无法知道其具体值，它是 **unbacked** 的（例如 `nonzero` 的输出第一维）。

## 11. Guards、assertions 与 Export contract

遇到对 shape 的条件时，它要么只涉及静态 shape（此时就是一个 `bool`），要么涉及动态 shape（此时是符号布尔表达式）。对后者：

- **条件只涉及 backed 动态 shape**：可以用这些动态 shape 的具体值把条件求值为 `True` 或 `False`，然后向 shape 环境里加一条 guard，说明对应的符号布尔表达式是 `True` 或 `False`，并继续追踪；
- **条件涉及 unbacked 动态 shape**：一般没有额外信息就无法求值，因此不能继续追踪，必须在导出时报错；用户应当使用显式的 PyTorch 算子让追踪继续。这些信息会作为 guard 加进 shape 环境，也可能帮助把之后遇到的其他条件求值为 `True` 或 `False`。

模型导出之后：

- **对 backed 动态 shape 的 guards** 可理解为对**输入动态 shape 的条件**。导出时必须提供一份**动态 shape 说明（dynamic shape specification）**，描述不仅示例输入、而且所有未来输入为使生成的代码正确而都应满足的动态 shape 条件。更准确地说，这份说明必须**在逻辑上蕴含**生成的 guards，否则导出时报错（并给出修改动态 shape 说明的建议）；反过来，如果没有对 backed 动态 shape 的 guards（特别是所有 shape 都是静态时），导出时就不需要提供动态 shape 说明。一般来说，动态 shape 说明会被转换成生成代码输入上的**运行时断言**；
- **对 unbacked 动态 shape 的 guards** 被转换成“内联（inline）”运行时断言，加在生成代码里这些 unbacked 动态 shape 被创建的位置——通常就在数据依赖算子调用之后。

区别可以这样记（笔者整理）：

| 来源 | 变成什么 | 作用 |
|---|---|---|
| backed 动态 shape 上的 guards | 对输入 shape 的运行时断言（由动态 shape 说明导出） | 定义导出 artifact **接受哪些输入** |
| unbacked 动态 shape 上的 guards | 生成代码内、数据依赖算子之后的内联断言 | 检查**运行中才产生**的动态事实 |

笔者补充一个示意（非文档原文）：设某个输入的 shape 为符号 $s_0$，追踪时看到 `if x.shape[0] > 16`，示例输入的 $s_0=20$，于是走真分支并记录 guard $s_0>16$；导出时提供的动态 shape 说明必须能推出 $s_0>16$（例如声明该维度的范围是 17 到 64），否则报约束违反。

## 12. 允许的算子、自定义算子、模块状态与 functionalization

### 12.1 允许的算子与自定义算子

所有 PyTorch 算子都被允许。此外可以定义并使用**自定义算子**；定义自定义算子需要像其他 PyTorch 算子一样为它定义 **fake 实现**（见 10.2 节）。文档的例子是一个包装 NumPy 的自定义 `sin` 算子及其（平凡的）fake 实现：

```python
@torch.library.custom_op("mylib::sin", mutates_args=())
def sin(x: Tensor) -> Tensor:
    x_np = x.numpy()
    y_np = np.sin(x_np)
    return torch.from_numpy(y_np)

@torch.library.register_fake("mylib::sin")
def _(x: Tensor) -> Tensor:
    return torch.empty_like(x)
```

**逐行解释**：`@torch.library.custom_op("mylib::sin", mutates_args=())` 注册名为 `mylib::sin` 的自定义算子，`mutates_args=()` 声明它不修改任何参数；函数体把张量转成 NumPy 数组、算 `np.sin`、再转回张量，这是真实实现（带数据）；`@torch.library.register_fake("mylib::sin")` 注册 fake 实现：`torch.empty_like(x)` 只说明输出与输入同 shape、同 dtype，不做任何真实计算。

有时自定义算子的 fake 实现涉及**数据依赖的 shape**。文档给出自定义 `nonzero` 的 fake 实现的样子：

```python
...

@torch.library.register_fake("mylib::custom_nonzero")
def _(x):
    nnz = torch.library.get_ctx().new_dynamic_size()
    shape = [nnz, x.dim()]
    return x.new_empty(shape, dtype=torch.int64)
```

**读法**：`new_dynamic_size()` 创建一个新的动态大小（无后备的符号），作为输出第一维 `nnz`（非零个数）；输出 shape 是 `[nnz, x.dim()]`，dtype 为 `int64`。原文用 `...` 省略了代码的前面部分（推测是该算子的真实实现与注册）。

### 12.2 模块状态：读取与更新

模块状态包括参数、buffer 和普通属性。普通属性可以是任何类型；参数和 buffer 总是张量。模块状态可以按前述类型规则是动态或静态：例如 `self.training` 是 `bool`，所以是静态的；任何参数或 buffer 都是动态的。模块状态里所含张量的 shape **不能是动态的**，即在导出时固定，导出程序的多次执行之间不能改变。

**访问规则**：

- 所有模块状态必须已初始化，访问未初始化的状态在导出时会报错；
- 读取模块状态总是允许的；
- 更新模块状态是可能的，但必须遵守：
  - **静态普通属性**（如原始类型）可以更新；读和更新可以任意交错，读取总会看到最新的更新值；因为这些属性是静态的，值也会被烧进去，所以生成的代码里没有任何真正“get”或“set”这类属性的指令；
  - **动态普通属性**（如张量类型）**不能更新**；要更新就必须在模块初始化时把它注册为 buffer；
  - **buffer** 可以更新，既可以原地（如 `self.buffer[:] = ...`）也可以不原地（如 `self.buffer = ...`）；
  - **参数**不能更新。通常参数只在训练时更新、推理时不更新；文档建议用 `torch.no_grad()` 导出，避免导出时发生参数更新。

### 12.3 Functionalization 的效果

任何被读取和/或更新的动态模块状态，会被分别“提升（lift）”为生成代码的输入和/或输出。导出程序在生成的代码之外，还保存参数和 buffer 的初始值以及其他张量属性的常量值。

笔者补充（文档没有展开）：后端更喜欢函数式的图——输出只由显式输入决定，修改变成返回更新后的值，别名关系被显式处理，后端 pass 不必模拟完整的 Python 对象状态。所以这不是简单地“禁止原地修改”，而是把副作用分层：图内的计算函数化，图外的包装处理必要的状态更新。

## 13. Dynamic shape 不等于不专门化

### 13.1 动态 shape 的动机

文档（Dynamic Shapes 页）的说法：动态 shape 让 PyTorch 模型能处理不同维度的输入而**无需重编译**，使同一个编译产物能处理不同的批大小、序列长度或图像尺寸；其原理是对张量维度做符号追踪而不是用具体值，从而得到一张在运行时能适应不同输入 shape 的计算图。**默认情况下，PyTorch 假定所有输入 shape 是静态的。**

通常深度学习编译器只支持静态 shape，输入 shape 变化就需要重编译。这种做法覆盖许多用例，但有几种情形不够用：

| 情形 | 文档的例子 |
|---|---|
| 可变维度（Variable Dimensions） | 批大小或序列长度会变，如自适应批处理 |
| 数据依赖的输出（Data-Dependent Outputs） | 模型输出取决于输入数据，如检测模型里数量可变的边界框 |
| 稀疏表示（Sparse Representations） | 处理过程依赖数据变化的稀疏结构，如稀疏张量、不规则（jagged）张量、图神经网络 |

动态 shape **不支持动态 rank** 的程序（输入张量维数变化的程序），因为这类程序罕见且不必要地复杂。

### 13.2 “让一个大小动态”意味着什么

文档的例子：函数 `f(x)` 若按静态大小编译，对不同大小就要重编译：

```python
import torch
@torch.compile(dynamic=False)
def f(x):
     return x* x.size()[0]

f(torch.rand(10))
f(torch.rand(20))
f(torch.rand(30))
f(torch.rand(40))
```

文档说：在产生的输出里可以看到生成了**四张图**（对应 tlparse 输出，快照里没有保存）。让大小动态后，函数无需重编译就能处理各种大小：

```python
import torch
@torch.compile(dynamic=True)
def f(x):
     return x* x.size()[0]

f(torch.rand(10))
f(torch.rand(20))
f(torch.rand(30))
f(torch.rand(40))
```

开启动态 shape 后**只生成一张图**。文档说这个小例子里编译时间差别很小，更复杂的用例会显示出显著的性能改进。文档的注释还强调，这里为简单起见用了 `@torch.compile(dynamic=True)`，但这个选项因为容易出错而不被推荐，推荐的开启方式见第 14 节。

**读法**：`x * x.size()[0]` 中 `x.size()[0]` 是传给乘法的整数。静态编译时它是常量（10、20、30、40 各是一个常量），每个新大小都破坏 guard，所以编译出四张图；动态编译时它是符号整数，同一张图对所有大小都成立。

### 13.3 什么是专门化（specialization）

**专门化**指通过检查控制流中的 shape 条件，为特定的输入 shape 优化计算图：如果某个分支是基于 shape 条件走的，图就为该条件量身定制；若新的输入不满足这个条件，系统就会重编译该图。专门化让你能为特定输入 shape 创建优化过的计算图，可以显著提高执行速度。文档的例子：

```python
import torch
@torch.compile(dynamic=True)
def f(x):
    if x.size()[0] == 10:
        return x * 10

    if x.size()[0] <= 30:
        return x*200

    return x*x.size()[0]

f(torch.rand(10))
f(torch.rand(20))
f(torch.rand(30))
f(torch.rand(40))
f(torch.rand(50))
```

文档说：这段代码专门化“图需要输入大小为 10，此时返回 `x * 10`；若输入大小小于 30，返回 `x * 200`”，在输出里可以看到这会产生**三张图**（文档还附有一张展示这三张图的示意图 `dynamic_shapes_example_specialization.png`，快照中没有保存）。

笔者推导（与文档“三张图”的说法一致）：代码里第二个条件是 `<= 30`（文档正文写作“小于 30”，以代码为准）。五次调用对应：`f(10)` 满足第一个条件，得到图 1（`x * 10`）；`f(20)` 与 `f(30)` 不等于 10 且 $\le30$，共用图 2（`x * 200`）；`f(40)` 与 `f(50)` 大于 30，共用图 3（`x * x.size()[0]`，大小仍是符号整数）。

**要点**：dynamic shape 用符号整数表示动态维度，但程序仍可按条件专门化；不同的 shape 范围可能需要不同的编译版本。动态的意义是**一个版本可覆盖一组值**，不是所有输入共享一份机器码。

## 14. Automatic dynamic 与开启动态行为的各种方式

文档列出让事物变动态的几种办法：

| 办法 | 做什么 | 文档的态度 |
|---|---|---|
| Automatic dynamic（自动动态） | 默认行为：首次编译假定静态 shape，同时跟踪这次编译的输入大小；触发重编译时，据此识别哪些维度变了，在第二次编译里把它们标成动态 | 默认 |
| User annotations（用户标注） | 用若干 API 显式地按名字或按代码把特定输入标成动态：避免本来最终会变动态的初始编译；也用来标记不会自动变动态的元素，如神经网络模块参数等 | **首选** |
| `torch.compile(dynamic=True)` | 强制所有大小和整数都动态 | **不推荐**，仅用于测试 |
| Advanced Options（高级选项） | 用于高级用例 | 见 Advanced Options to Control Dynamic Behavior（本快照未包含） |

`torch.compile` 的 `dynamic` 参数有三种取值（Dynamo Core Concepts 页的说法）：默认是 `dynamic=None`（自动动态：若因 shape 不匹配导致需要重编译，就用动态 shape 重试），也可以完全开启（`dynamic=True`）或完全关闭（`dynamic=False`）。

默认策略保留了首个 shape 的专门化版本（笔者补充：这通常使首个 shape 的 kernel 质量最好），代价是产生一次额外的编译；用户已知变化的维度时，可以提前标注。

## 15. 标注 API 的使用边界

### 15.1 `mark_dynamic(tensor, dim, min=..., max=...)`

- **只能作用于输入**：必须在调用 compiled function 之前，对输入张量调用；**不得**在正在被 `torch.compile` 编译的函数里（如模型的 `forward()` 或它调用的任何函数）调用，否则 Dynamo 会报类似 `AssertionError: Attempt to trace forbidden callable` 的错误（这是追踪期 API）。正确用法：`torch._dynamo.mark_dynamic(x, 0)`，然后 `compiled_model = torch.compile(model)`；
- 它把张量的某一维标成动态，**如果该维被专门化就失败**；不适用于整数；只有当你知道使用该输入的这个 frame 里所有图会**收敛成一张动态图**时才用，否则可能遇到有误导性的约束违反错误，此时考虑 `maybe_mark_dynamic()`；
- 目前它**不优先于** `force_parameter_static_shapes = True` 或 `force_nn_module_property_static_shapes = True`；
- 若事先知道某维会动态，可用它避免初始的那次重编译；若已知该维的最小和最大可能值，可用 `min=`、`max=` 指定。

文档的快速例子：

```python
import torch

@torch.compile
def f(x):
    return x * x.size()[0]

x = torch.randn(10)
torch._dynamo.mark_dynamic(x, 0)

# first invocation we give it is a tensor marked as dynamic
f(x)
# rest of these invocations will use dynamically compiled code
f(torch.randn(20))
f(torch.randn(30))
f(torch.randn(40))
```

**读法**：第一次调用就传入被标成动态的张量，所以第一次编译就产生动态图，之后大小 20、30、40 的调用都复用这张图，没有额外重编译。

### 15.2 `maybe_mark_dynamic(tensor, dim)`

与 `mark_dynamic()` 具有全部相同的性质，但**即使大小被专门化也不失败**。用于被多张图共享的输入，或某个 frame 里图的数量不会收敛到一张的情形。例如上面的例子里，应使用 `maybe_mark_dynamic()`，因为大小为 0 和 1 的图会被专门化；但如果要保证永不专门化，可以用 `mark_dynamic()`。（笔者补充：大小 0/1 的特判是一个常见原因，见 [PyTorch 2 论文解读](../pytorch_2/论文中文解读.md)第 5.2 节“0/1 特化”。）

### 15.3 `mark_unbacked(tensor, dim)`

把张量的某维标成 unbacked。文档说它**不太可能是你需要的工具**，但当专门化发生在某个条件 `guard_size_oblivious(x)` 里，并且使用它能消除专门化时可能有用；要确保它确实修好了专门化，而且没有引入一个数据依赖错误（该错误会转成发生在你想避免的专门化位置处或其之前的 graph break）。文档说下一个选项可能更好。

### 15.4 动态白名单与静态白名单

| 选项 | 机制 | 要点 |
|---|---|---|
| 动态白名单 `DYNAMIC_SOURCES` | 用环境变量 `TORCH_COMPILE_DYNAMIC_SOURCES` 传入一组 source 名称，标成动态，例如 `TORCH_COMPILE_DYNAMIC_SOURCES=L['x'],L['y']`；也可写成 `torch.compiler.config.patch(dynamic_sources="L['x']")` | 用 tlparse 里的 PGO artifact 最容易找到这些名称，可复制粘贴；对整数和张量大小都有效；对所有强制静态 shape 的其他开关有**最高优先级**；如果被标成动态的东西被专门化、或给定的输入不存在，**不报错** |
| 静态白名单 `STATIC_SOURCES` | 动态白名单的反面：用环境变量 `TORCH_COMPILE_STATIC_SOURCES`（或 `torch.compiler.config.static_sources`）传入一组应保持静态的 source 名称 | 适用于自动动态或 PGO 把某物变成动态而这种动态性有害（例如产生了更差的 kernel）；接受与动态白名单相同的精确名称、正则和 `:N` 每维语法；对整数和张量大小都有效；条目会覆盖自动动态、PGO 和 `dynamic=True`，但**不覆盖**显式的 `torch._dynamo.mark_dynamic()` |

文档的例子（动态白名单与静态白名单）：

```python
import torch

@torch.compile()
def f(x):
     return x * x.size()[0]

with torch.compiler.config.patch(dynamic_sources="L['x']"):
    f(torch.rand(10))
f(torch.rand(20))
f(torch.rand(30))
f(torch.rand(40))
```

```python
import torch

@torch.compile()
def g(x):
     return x * x.size()[0]

with torch.compiler.config.patch(static_sources="L['x']"):
    g(torch.rand(10))
    g(torch.rand(20))
    g(torch.rand(30))
```

**读法**：`L['x']` 是名为 `x` 的局部变量的 source 名称（`L` 表示局部作用域；这个记法文档未展开，笔者按字面理解）。前一个例子里首次编译在 `patch` 上下文中把 `x` 的大小标成动态，之后不同大小的调用沿用动态图；后一个例子相反，在 `patch` 上下文内把 `x` 强制保持静态。

### 15.5 `torch.compiler.set_stance("eager_then_compile")` 与 `dynamic=True`

有时确定该标哪些输入为动态很难。如果愿意为第一个批次付出性能代价，另一个方便的选项是 `eager_then_compile` 这类 stance，它会**自动替你判断动态输入**（详见 `torch.compiler.set_stance()`）。

`torch.compile(dynamic=True)` 会强制**所有**大小和整数都动态，增加遇到动态 shape bug 的可能；让每个输入大小都动态还可能造成性能退化并最终增加编译时间，所以文档不推荐设置它，适合诊断而不是默认万能开关（后半句是笔者的归纳）。

### 15.6 “接下来怎么办”

文档的建议：如果遇到框架代码的 bug 或专门化的问题，请提交 issue；如果问题出在用户代码里，考虑是否愿意重写代码来避开它，并判断它是否影响正确性或只是冗余检查；如果问题涉及带 `constexpr` 参数的 Triton 自定义 kernel，评估能否重写来解决。

## 16. 一套实用诊断顺序

以下顺序是笔者的整理（不是这四个页面的原文），把上面各节串成排查路径。

### 先看 correctness

- export 是否捕获了期望的路径（静态值被烧进图、可选输入被专门化）；
- mutation/alias 语义是否保持（模块状态的读写规则、functionalization 的提升）；
- 自定义算子是否有 fake 实现；
- 动态 shape 说明是否覆盖未来的输入。

### 再看 graph quality

- graph break 在哪里；
- 每个 region 多大；
- 是否有意外的常量专门化；
- 是否确实需要高阶控制流算子（`torch.cond`、`torch.map`）。

### 再看 cache behavior

- guard 失败的原因；
- 同一个 frame 有多少个版本；
- shape 变化是否收敛到符号图（automatic dynamic 或显式标注）；
- 编译与热身是否计入延迟。

### 最后看 backend

- 融合与生成的 kernel；
- 动态下标的代价；
- kernel 是否为范围内的主要 shape 选择了好的调度。

## 17. 常见误读

### “torch.compile 会先得到完整的静态图”

默认可以得到多个 FX 区域，中间仍运行残余的 Python（见 4.3 节 `torch.save` 的例子）。

### “graph break 只影响编译时间”

文档说 graph break 可能导致意料之外的变慢并阻碍后端优化机会，也就是还影响稳态运行；笔者补充：包括 launch 次数、融合与中间张量物化。

### “dynamic shape 会自动接受任意输入”

图仍受 rank、dtype、device、范围和路径 guards 的约束；动态 shape 不支持动态 rank。

### “torch.export 比 compile 更灵活”

恰好相反：export 的目标是得到一张独立的、带元数据的图，静态值被烧进图、数据依赖的控制流必须用显式算子，对完整图和约束更严格（笔者补充：它不能像 `torch.compile` 那样靠 graph break 回到 eager）。

### “输入是函数参数，就一定是图的运行时输入”

不是：静态输入（原始类型等）被写死进图，导出后传不同的值会出错；未传入的可选输入会专门化到默认值。

### “给 `dynamic=True` 就一劳永逸”

文档把它列为不推荐、仅用于测试；用户标注才是首选。

## 18. 最终判断

现代 PyTorch graph system 的核心不是把动态图改成静态图，而是管理一组**有条件成立的图表示**：用 guards 定义复用范围，用 graph break 保持兼容，用符号 shape 扩大覆盖，再用 export 把可部署的契约显式化。
